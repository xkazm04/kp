## 2. `resumeAnalysis` duplicates the entire success/abort tail of `executeAnalysis`
- **Severity**: Medium
- **Category**: duplication
- **File**: `app/features/sub_analyze/runAnalysis.ts:48-77` (`executeAnalysis` L48-64 and `resumeAnalysis` L68-77)
- **Evidence**: After `executeAnalysis` does its submit-specific prefix (`submitAnalysis` + `onTaskStarted`), both functions run a byte-identical tail: `const parsed = await watchAnalysis(taskId, callbacks.onProgress, signal); callbacks.onFinalize(); window.setTimeout(() => callbacks.onResult(parsed), 320);` followed by an identical `catch (caught) { if (isAbort(signal, caught)) return; callbacks.onError(caught instanceof Error ? caught.message : "Analysis failed."); }`. Grep `setTimeout\(\(\) => callbacks.onResult` returns the two copies (L59, L72); the catch blocks (L60-63, L73-76) are character-for-character the same including the magic `320` and the fallback string. Both are live: grep `resumeAnalysis|executeAnalysis` shows `resumeAnalysis` called at `useAnalyzeForm.ts:277` and `executeAnalysis` at `useAnalyzeForm.ts:411`. This is plain logic duplication, NOT the intentional AbortSignal-threading hardening the conventions warn about — the signal plumbing stays untouched; only the shared resolve/error tail is factored out.
- **Impact**: The completion delay (`320`), the abort-vs-error decision, and the fallback message must be kept in sync across two functions; a fix to one (e.g. the bug-hunt history shows this file already churns) can silently miss the other.
- **Fix sketch**: Extract a private `await settleAnalysis(taskId, callbacks, signal)` holding the shared `watchAnalysis → onFinalize → setTimeout(onResult,320)` + the `catch`/`isAbort` tail. `resumeAnalysis` becomes `return settleAnalysis(taskId, callbacks, signal)`. `executeAnalysis` keeps its submit prefix (`submitAnalysis` + `onTaskStarted`) then `await settleAnalysis(taskId, callbacks, signal)`. No external callers change (both keep their signatures).

## 3. Triplicated consecutive-error bail block inside `watchAnalysis`
- **Severity**: Medium
- **Category**: duplication
- **File**: `app/features/sub_analyze/AnalyzeApi.ts:76-99` (blocks at L77-80, L86-90, L94-98)
- **Evidence**: The poll loop repeats the same guard three times — once for a thrown `fetch` (L78), once for a non-OK response (L87), once for a missing `task` body (L95): `if ((consecutiveErrors += 1) >= MAX_CONSECUTIVE_ERRORS) { throw new Error("Lost track of the analysis — please retry."); } continue;`. Grep `consecutiveErrors \+= 1` returns exactly these three sites, all in this file. The error string and threshold are duplicated literally each time. This is poll robustness boilerplate (not signal threading), so consolidating it doesn't touch the AbortSignal hardening.
- **Impact**: Three copies of the same threshold check and user-facing message; changing the message or the "what counts as a soft failure" rule means editing all three, and a missed copy diverges silently.
- **Fix sketch**: Add a small local `const softFail = () => { if ((consecutiveErrors += 1) >= MAX_CONSECUTIVE_ERRORS) throw new Error("Lost track of the analysis — please retry."); };` inside `watchAnalysis` (closing over the local counter). Replace each of the three blocks with `softFail(); continue;`. Behavior is identical; the 404 terminal check (L85) and the `consecutiveErrors = 0` reset on a good poll (L100) stay as-is.
