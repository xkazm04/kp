## 1. Confidence-band range (`low–high` + badge) re-rendered inline at every match surface
- **Severity**: Medium
- **Category**: duplication
- **File**: `app/features/sub_match/MatchCard.tsx:86-90,102` and `app/features/sub_match/JobCompare.tsx:78-81` (same cluster also in `app/features/sub_decisions/AnalysisSummaryModal.tsx:127-130`, `app/features/sub_decisions/group-eval/ComparisonCells.tsx:32-35`, `app/features/sub_jobs/RecruiterCandidates.tsx:431-434`)
- **Evidence**: Every consumer of a `MatchResult`/`MatchResultView` hand-rolls the identical 3-part cluster: `<span title={confidenceBandTitle(x.confidence.drivers)}>{x.confidence.low}–{x.confidence.high}</span>` immediately followed by `<ConfidenceBandBadge level={x.confidence.level} drivers={x.confidence.drivers} />`. `Grep "confidence.low|confidenceBandTitle|ConfidenceBandBadge"` over `app/` returns this same triple at 5 distinct call sites (2 in this context: MatchCard, JobCompare). The two helpers (`confidenceBandTitle`, `ConfidenceBandBadge`) already live in `app/_components/Badge.tsx`, but the `low–high` numeric span — the part that reads `confidence.drivers` a *second* time for the title and assumes the `nums`/`tabular-nums` styling — is copy-pasted, not shared.
- **Impact**: Five copies of one micro-layout. A change to how the band reads (e.g. show the band only when not `tight`, swap the en-dash, add an aria-label) must be applied in 5 places or surfaces silently diverge; `confidence.drivers` is threaded into both the span title and the badge at each site, doubling the drift surface. Pure presentation, so the risk is inconsistency, not a logic bug.
- **Fix sketch**: Add a `ConfidenceBand({ confidence }: { confidence: Confidence })` to `Badge.tsx` (beside the existing `ConfidenceBandBadge`) that renders the titled `{low}–{high}` span + the badge as one unit. Replace the inline clusters in MatchCard, JobCompare (and, opportunistically, the 3 out-of-context sites that import the same helpers). All five already import from `@/app/_components/Badge`, so no new import path.

## 2. Matrix score-band edges (45 / 60 / 72 / 85) hard-coded in three independent places
- **Severity**: Medium
- **Category**: duplication
- **File**: `app/features/sub_matrix/MatrixShared.tsx:14-22` (`cellClass`), `app/features/sub_matrix/MatrixShared.tsx:26,66-79` (`BAND_FILL` + `MatrixLegend` literal labels), `app/features/sub_matrix/matrix-stats.ts:8-9` (`STRONG_THRESHOLD` + `BAND_EDGES`)
- **Evidence**: The same 5-band diverging scale with edges `45/60/72/85` is encoded three times with no shared source: (a) `cellClass` branches on `s < 45 / < 60 / < 72 / < 85`; (b) `matrix-stats.ts` declares `BAND_EDGES = [45, 60, 72, 85]` for the histogram buckets; (c) `MatrixLegend` hard-codes the human labels `"<45","45–59","60–71","72–84","85+"` as bare strings, and `BAND_FILL` lists 5 colors in the same band order as `cellClass`'s 5 return values. `Grep "BAND_EDGES|cellClass|45|72|85"` over `sub_matrix/` confirms the edges live in both files and the legend strings restate them a third time. The code comments even cross-reference each other ("the moss threshold cellClass uses (s >= 72)", "bands match the legend"), i.e. the coupling is acknowledged but not enforced.
- **Impact**: Re-banding the heatmap (a likely tuning request — the comment notes "on a real pool the grid is mostly weak cells") means editing thresholds in `cellClass`, the edge array in `matrix-stats.ts`, the fill array AND the literal label strings in `MatrixLegend`, with nothing to catch a missed one. A legend that says "60–71" over a `cellClass` that actually breaks at 62 is an undetectable correctness/trust drift on a hiring grid.
- **Fix sketch**: Promote a single `MATRIX_BANDS` table in `matrix-stats.ts` — an ordered array of `{ min, label, cellClass, fill }` (the existing `BAND_EDGES`/`STRONG_THRESHOLD` derived from it). Drive `cellClass`, `BAND_FILL`, the legend rows, and `columnStats`' bucket loop off that one array. `cellClass` becomes a lookup; `MatrixLegend` maps over the table instead of a literal `[[cls,label]...]`; the histogram keeps using the derived edges. No behavior change, three encodings collapse to one.

## 3. Reasoning verdict/strengths/gaps/probes rendered by two separate components
- **Severity**: Medium
- **Category**: duplication
- **File**: `app/features/sub_matrix/MatrixTab.tsx:715-760` (inline popover renderer) vs `app/features/sub_match/MatchShared.tsx:67-131` (`ResolvedReasoning` + `ReasonList`)
- **Evidence**: Both surfaces render the identical `Reasoning` shape (`{ verdict, strengths[], gaps[], interviewProbes[] }`, type in `MatchTypes.ts:117`). `MatchShared.tsx` has `ResolvedReasoning` → three `ReasonList` columns (strengths/gaps/probes) + verdict + source/cached chip. `MatrixTab.tsx` re-implements the same thing inline inside the popover: a verdict `<p>`, then three `<div>` blocks each titled strengths/gaps/probes with a bulleted `<ul>`, plus a deterministic-source note. `Grep "ResolvedReasoning|ReasonList"` shows both are **module-private** to MatchShared (never exported), which is why MatrixTab couldn't reuse them and grew a parallel copy. Both even apply the same green/coral/steel tone-per-list convention by hand.
- **Impact**: Two renderers for one data shape. The matrix copy already drifted (it slices `strengths/gaps` to 4 and `probes` to 3 and shows a different "deterministic" note), so the two reasoning views don't match. Any future change to how a rationale reads (ordering, empty-list handling, a new field) must be done twice. ~45 lines of avoidable JSX in MatrixTab, which is already a 779-line component.
- **Fix sketch**: Export a presentational `ReasoningBody({ r, source }: { r: Reasoning; source?: string })` from `MatchShared.tsx` (extract the inner markup of `ResolvedReasoning`, minus the motion wrapper). Have `ResolvedReasoning` wrap it, and replace the MatrixTab popover's inline IIFE (lines ~722-758) with `<ReasoningBody r={d} source={st.source} />`. Keep MatrixTab's loading/error/`!data` guards local; only the resolved body is shared. Note: this is the *renderer* only — the data fetch paths legitimately differ (background task vs direct `/api/match/reasoning`) and should stay separate.

## 4. `salaryBand` "k CZK" thousands formatter duplicated across MatchCard and JobCompare
- **Severity**: Low
- **Category**: duplication
- **File**: `app/features/sub_match/MatchCard.tsx:147-149` vs `app/features/sub_match/JobCompare.tsx:15`
- **Evidence**: Both produce the abbreviated-thousands band string from a `MatchResult.salaryBand: number[]`. MatchCard inlines `m.salaryBand.length === 2 ? \`${Math.round(m.salaryBand[0]/1000)}–${Math.round(m.salaryBand[1]/1000)}k CZK\` : "—"`; JobCompare declares `const fmtBand = (b?: number[]) => (b && b.length === 2 ? \`${Math.round(b[0]/1000)}–${Math.round(b[1]/1000)}k\` : "—")` then appends `"CZK"` separately. `Grep "/ 1000"` over `sub_match/` returns exactly these two. (Distinct from the app-wide `formatSalaryRange` in `app/_lib/format.ts`, which renders the *full* grouped form "45 000–60 000 CZK" — the match surfaces deliberately use the compact "45–60k" style, so this is its own small helper, not a call to the existing one.)
- **Impact**: Minor. Two encodings of the same compact-band rule; the suffix is even attached inconsistently (baked into MatchCard's literal vs appended after `fmtBand` in JobCompare), so the two can drift on spacing/currency.
- **Fix sketch**: Add a `formatBandCompact(band?: number[]): string` to `MatchShared.tsx` (or `MatchTypes.ts`) returning `"45–60k CZK"` / `"—"`, and call it from both. Folds two implementations and the inconsistent suffix handling into one.
