## 2. Duplicated client-side `/api/pipeline/[id]` action POST wiring across 4 call sites
- **Severity**: Medium
- **Category**: duplication
- **File**: `app/features/sub_pipeline/PipelineTab.tsx:447-457` (bulkMove), `:481-491` (bulkDecide), `:512-518` (moveEntry); `app/features/sub_pipeline/CandidateDrawer.tsx:304-311` (moveStage)
- **Evidence**: Grep `fetch(\`/api/pipeline/${encodeURIComponent` finds four mutating calls, each hand-rolling the identical request: `fetch(\`/api/pipeline/${encodeURIComponent(id)}\`, { method: "POST", headers: { "Content-Type": "application/json" }, body: JSON.stringify({ action, ... expectedStage }) })`. `set_stage` bodies (grep `action: "set_stage"`: PipelineTab:451, PipelineTab:516, CandidateDrawer:308) are byte-for-byte the same shape; the accept/reject body (PipelineTab:482-486) differs only in dropping `toStage`. This is the *transport wiring* duplication, NOT the `expectedStage` CAS guard itself — the per-caller CAS value is intentional (the prompt's convention (b), preserved by passing `expectedStage` as an argument). The repo already has the canonical pattern for exactly this: `useAddToPipeline.ts` factored its add-POST into `postPipelineAdd(...)` "so the error handling the two copies kept re-implementing ... lives and is tested in one place."
- **Impact**: Four copies of headers + `JSON.stringify` + `r.ok` handling drift independently (e.g. CandidateDrawer reads `data.error` from the body; PipelineTab's loops ignore it). A future change to the action contract (a new header, an error-shape read) must be applied in 4 places or they diverge.
- **Fix sketch**: Add a tiny helper beside the existing `postPipelineAdd`, e.g. `postPipelineAction(id, body): Promise<Response>` (or a typed `{ ok; entry?; error? }` result mirroring `postPipelineAdd`). Have `moveEntry`, `bulkMove`, `bulkDecide`, and CandidateDrawer's `moveStage` call it with their own `expectedStage`/`action`/`toStage`. Pure mechanical extraction; the CAS semantics and per-caller optimistic/rollback logic stay in the callers.

## 3. Duplicated lane-key derivation between `groupPositions` and the board lane filter
- **Severity**: Medium
- **Category**: duplication
- **File**: `app/features/sub_pipeline/PipelineTab.tsx:65` (`groupPositions`) and `app/features/sub_pipeline/PipelineBoard.tsx:254` (lane filter)
- **Evidence**: Grep `jobId ?? ... jobTitle ?? "?"` finds the position key computed in two files: PipelineTab.tsx:65 `const key = e.jobId ?? e.jobTitle ?? "?";` (drives the `positions`/`boardPositions` count) and PipelineBoard.tsx:254 `entries.filter((e) => (e.jobId ?? e.jobTitle ?? "?") === pos.id)` (drives which entries render in each lane). These two MUST stay identical or an entry is counted in one lane and rendered in another. This exact mismatch was a shipped bug: `docs/harness/bug-hunt-2026-06-07/pipeline-board-scheduler.md` documents the 2-way-vs-3-way fallback divergence (`(null ?? null) === "?"` → false), and PipelineBoard.tsx:250-254 carries an inline comment warning the keys must match. They currently agree, but the keying is still copy-pasted, so the safeguard is "two comments" rather than one function.
- **Impact**: Latent correctness fragility, not a present bug. Any future tweak to the key (e.g. add a tertiary fallback, normalize whitespace) re-opens the count-vs-render split unless both copies change in lockstep — the precise failure mode that already cost one bug-hunt cycle.
- **Fix sketch**: Add `export function entryLaneKey(e: Pick<Entry, "jobId" | "jobTitle">): string { return e.jobId ?? e.jobTitle ?? "?"; }` to PipelineTypes.ts. Call it from `groupPositions` (PipelineTab) and the lane filter (PipelineBoard) so the count and lane membership are provably computed by one function.
