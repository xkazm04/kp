## 2. Triplicated commit-list → CommitEntry mapping inside repo-snapshot.ts
- **Severity**: Medium
- **Category**: duplication
- **File**: `app/_lib/repo-snapshot.ts:87-90, 119-123, 182-186`
- **Evidence**: The same "GitHub commits API row → first-line, length-clamped commit summary" transform is hand-written three times in one file. `fetchCommitTrace` (119-123) and `fetchRepoSignals` (182-186) build a `CommitEntry` with byte-for-byte identical bodies: `sha: (c.sha ?? "").slice(0,7)`, `message: (c.commit?.message ?? "").split("\n")[0].slice(0,140)`, `date: c.commit?.author?.date ?? ""`. `buildRepoSnapshot` (87-90) repeats the message-extraction half (`.split("\n")[0].slice(0,100)`). This is genuine copy-paste of the transform logic, NOT the intentional `github-summary.ts` build/coerce shape-authority pattern. Grep `\.split("\n")\[0\]` confirms the three in-file sites (plus one more in the route — see finding 3).
- **Impact**: The 7-char SHA slice and the message-first-line slice are tuned constants that can silently drift between the snapshot path and the signals path; a fix to one (e.g. handling a missing `author.date`) is easy to forget in the other two.
- **Fix sketch**: After removing the dead `fetchCommitTrace` (finding 1), only two sites remain. Extract a tiny pure local helper `toCommitEntry(c): CommitEntry` (and/or a `firstLine(msg, max)` helper) and call it from both `fetchRepoSignals`'s `list.map(...)` and `buildRepoSnapshot`'s `recentCommitSummaries`. Keep it module-local — the file is intentionally import-free for its colocated node --test, so do not move it to a sibling.

## 3. Commit-subject extraction repeated across the route and snapshot module

- **Category**: duplication

- **Evidence**: The "first line of a commit message" idiom appears in four places. Route `fetchRepoBundle` does `commits.map((c) => c.commit?.message?.split("\n")[0] ?? "").filter(Boolean).slice(0, COMMITS_PER_REPO)` (459-462); `repo-snapshot.ts` does `(c.commit?.message ?? "").split("\n")[0].slice(0, N)` at three sites. Grep `split("\n")[0]` over `app/` returns exactly these four lines and nothing else. The route also re-declares its own GitHub commit row shape (`Array<{ commit?: { message?: string } }>`) that the snapshot module already models. Note: this crosses the route↔lib boundary, and `repo-snapshot.ts` is deliberately self-contained for its colocated test, so a SHARED extraction is the wrong move here — the safe consolidation is within each module.
- **Impact**: Low-risk but real: the same parse appears in two subsystems (the live deep-review payload and the dev-case signals), so the convention ("subject = first line, trimmed/clamped") is implicit and unenforced. New callers reinvent it.
- **Fix sketch**: Do NOT cross the module boundary. Within the route, fold the inline map into the same module-local `firstLine` helper used by `fetchReadme`-adjacent code if one is introduced; within `repo-snapshot.ts` reuse the helper from finding 2. Leave the two helpers as independent copies (one per module) — this respects the import-free test constraint while removing the in-module repetition. If only one change is made, prefer finding 2 (same-file dedup) and leave the route as-is.

## 4. Two parallel GitHub fetch/header layers with divergent error semantics
- **Severity**: Low
- **Category**: structure
- **File**: `app/_lib/repo-snapshot.ts:28-61` (`GH`, `ghHeaders`, `gh`) and `app/api/github-analysis/route.ts:262-282` (`githubFetch`)
- **Evidence**: Both wire up `Accept: application/vnd.github+json`, conditionally attach a `Bearer ${GITHUB_TOKEN}` auth header, and `fetch(url, { headers, next: { revalidate: 0 } })`. They differ deliberately: `repo-snapshot.gh()` swallows errors to `null` and also honours `GH_TOKEN`; the route's `githubFetch` throws typed messages (404/403/other), adds `X-GitHub-Api-Version` + `User-Agent`, and reads only `GITHUB_TOKEN`. The header file comment ("Mirrors the fetch layer used by /api/github-analysis") acknowledges the copy. This is structural duplication, but the differing throw-vs-null contracts and the explicit "self-contained, no sibling imports" design note on `repo-snapshot.ts` (so its colocated node --test keeps resolving) mean a shared module would violate an intentional constraint.
- **Impact**: Header/auth drift risk — e.g. `repo-snapshot` omits the `User-Agent` and `X-GitHub-Api-Version` the route sends, and reads a second token env var the route doesn't. Low because both are small and each is tested/used in its own path; merging is speculative reorganization, not a mechanical win.
- **Fix sketch**: Leave as-is unless a shared, dependency-light `app/_lib/github-fetch-base.ts` (header builder + token resolution only, no error policy) is wanted; if so, each module keeps its own throw/null wrapper and imports only the header builder. Out of scope for a safe mechanical pass — recommend NOT changing now; documented here for awareness only.
