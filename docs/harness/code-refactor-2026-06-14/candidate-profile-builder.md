## 2. Education-level vocabulary is a hand-kept copy that contradicts the file's own "single source of truth" comment
- **Severity**: Medium
- **Category**: duplication

But `_EDU_LEVELS = {"phd","master","bachelor","university","unknown"}` (line 32) is itself the hand-kept copy the comment disclaims — it imports nothing. The identical literal list is repeated in the `DRAFT_SCHEMA` doc string (line 40), in `gemini.py:37`, and as the client `EDU_LEVELS` in `ProfileTypes.ts:97`. I confirmed there is no shared Python constant to import: `Grep "EDU_LEVELS|education_level|_EDU_LEVELS" path=pipeline/jobfit` shows `profile.py:112` defines `education_level: str = "unknown"` as a bare field (no enum), and `jobs.py:41` has a *different* `EDU_LEVELS` tuple ending in `"none"` (job-side minimum-education, deliberately distinct). If a full codegen wire-up is out of scope, the minimal honest fix is to correct the comment so it no longer claims education levels are centralized. Do not touch `jobs.py` `EDU_LEVELS` — different domain (adds `"none"`).

Verify the server file stays free of client-only imports after the change.

## 5. Duplicated comma/semicolon `splitList` helper
- **Severity**: Low
- **Category**: duplication
- **File**: `app/features/sub_profile/ProfileEditor.tsx:134-138`, `app/_lib/completeness-followup.ts:71-75`
- **Evidence**: `Grep "splitList" path=app` shows two private `splitList` implementations in scope that both "split on a delimiter, trim, drop empties." They are **not identical**: `ProfileEditor` uses `/[,\n;]+/` (also splits on newlines, collapses runs), `completeness-followup` uses `/[,;]/` (no newline, no run-collapse). A near-identical `/[,;]/` variant also lives at `app/_lib/apply-intake.ts:215` (out of this context's scope). All three are local and feed candidate intake list fields (languages/skills/aspirations).
- **Impact**: Low — small helpers, but three subtly-divergent copies of "parse a comma list" means a future fix (e.g. also split on `/`) lands in one and silently not the others. The newline-vs-no-newline divergence is itself a latent inconsistency in how the same kind of free-text list is parsed across the intake surfaces.
- **Fix sketch**: Extract one `splitList(text, { newlines?: boolean })` into a shared client-safe lib helper (e.g. `app/_lib/` next to other string utils) and have both call sites use it, preserving each one's current delimiter behavior via the option. Because the regexes differ, do this only with the option flag — a blind merge to one regex would change parsing semantics. Given the low value, acceptable to defer; documented here for completeness.
