## 1. Nine copies of the devcase-CLI spawn/parse scaffold in `devcase-run.ts`
- **Severity**: High
- **Category**: duplication
- **File**: `app/_lib/devcase-run.ts` (the 9 `run*`/`mint*` functions, e.g. lines 68-86, 106-135, 151-176, 193-218, 245-289, 328-371, 391-411, 460-546, 568-598)
- **Evidence**: `grep -c "const workdir = await createWorkdir();"` and `grep -c "pipeline.jobfit.devcase.devcase_cli"` in `devcase-run.ts` each return **9**; `grep -c "if (exitCode !== 0) throw new PipelineError(parseStderrError(stderr, exitCode))"` returns **9**. Every one of the nine functions repeats the identical envelope: `createWorkdir()` → write one-or-more `*.json` arg files → `spawnPython(["-m","pipeline.jobfit.devcase.devcase_cli", <verb>, ...args], { signal })` → `await result` → `if (exitCode !== 0) throw new PipelineError(parseStderrError(stderr, exitCode))` → `parsePythonJson<{ result; source; perStepSources?; fallbackReason? }>(stdout, stderr)` → `finally { await cleanupWorkdir(workdir) }`. No shared helper exists today: `grep "runDevcaseCli|devcaseCli|spawnDevcase|runCli"` across `app/_lib` → **no matches**. This is the single largest mechanical-dedup opportunity in the context (~480 LOC of body, the majority of it boilerplate).
- **Impact**: ~9x maintenance surface for one protocol. A change to the envelope (e.g. a new `--lang` default, a stderr-format tweak, adding `cleanupWorkdir` error handling) must be hand-applied nine times; the `signal` arg is already inconsistently forwarded (`runInterviewScenario`/`runMaterializeSeed`/`mintObserved*` omit it while `runNeedAnalysis`/`runDesignArtifacts`/`runEvaluateSubmission`/`runSourceForRole` pass it) — exactly the drift a single helper prevents. `ctx.signal` forwarding itself is the intentional kp SIGKILL convention and must be preserved by the helper, not removed.
- **Fix sketch**: Add one private helper in `devcase-run.ts`, e.g. `async function runDevcaseCli<T>(verb: string, files: Record<string, unknown>, extraArgs: string[] = [], signal?: AbortSignal): Promise<{ result: T; source: string; perStepSources: Record<string,string>; fallbackReason: Record<string,string> }>` that owns workdir lifecycle, writes each entry of `files` as `<key>.json` + appends `--<kebab(key)>-json <path>`, builds the `-m … devcase_cli verb` argv, runs the exitCode/parse/cleanup envelope, and normalizes the `?? {}` defaults once. Each `run*` function collapses to a single call plus its post-processing (e.g. `runEvaluateSubmission` keeps its `processTrace`/`authenticity`/`seedDiff` folding and `saveSubmissionEvaluation`). Forward `signal` uniformly. No callers change — all are internal.

## 2. Duplicate submission-intake + lifecycle-resume block in `submit` and `inbound` routes
- **Severity**: Medium
- **Category**: duplication
- **File**: `app/api/devcase/submit/route.ts:25-40` + `app/api/devcase/inbound/route.ts:45-56` (other affected: neither imports a shared helper today)
- **Evidence**: `grep "lifecycleByPosting(postingId)"` returns exactly the two files. Both routes import `{ intakeSubmission }` from `@/app/_lib/distribution` + `{ startTask }`, call `intakeSubmission({ postingId, candidateRef, repoRef, contact, notes })`, then run the byte-identical event-trigger: `if (isNew) { const lc = lifecycleByPosting(postingId); if (lc && lc.stage === "collecting") startTask("lifecycle", { lifecycleId: lc.id, title: lc.title }); }`. The only real differences are field naming (`body.candidateRef` vs `body.candidate`) and the credential model (submit takes `postingId`/`token`; inbound is the public token-only webhook — that auth divergence is intentional, see the inbound docstring, and must stay).
- **Impact**: The resume-on-new-submission rule (the heart of "submissions auto-resume a collecting lifecycle") lives in two places; a change to the trigger condition (e.g. also resuming a `ranked` lifecycle, or deduping the task differently) silently applies to only one intake path.
- **Fix sketch**: Extract a shared `resumeCollectingLifecycle(postingId: string): void` (resume block) — and optionally an `intakeAndResume(args, { isNewOnly })` wrapper — into `@/app/_lib/distribution` (where `intakeSubmission` already lives) or a small `devcase` lib. Both routes keep their own body-coercion + auth (hand-rolled coercers per kp convention) and call the shared resume after `intakeSubmission`.

## 3. `getPromoteFloor() ?? DEV_POLICY.promoteFloor` duplicated across orchestrator and outcomes route
- **Severity**: Medium
- **Category**: duplication
- **File**: `app/api/devcase/outcomes/route.ts:8` + `app/_lib/devcase-orchestrator.ts:241`
- **Evidence**: `grep "getPromoteFloor() ?? DEV_POLICY.promoteFloor"` returns exactly these two sites. The outcomes route defines `const activeFloor = () => getPromoteFloor() ?? DEV_POLICY.promoteFloor;` and the orchestrator's `ranked` stage inlines `const floor = getPromoteFloor() ?? DEV_POLICY.promoteFloor;`. Both encode the same "calibrated override else policy default" contract; both already import `DEV_POLICY` (orchestrator owns it; the route imports it). `getPromoteFloor` returns `null` when unset by design (see `dev-control.ts:86-90`), so the fallback is load-bearing and must stay co-located with the default.
- **Impact**: The promote-floor resolution rule (the live threshold a human's calibration actually moves) is defined twice; if the default source or null-handling changes, the calibration-display floor and the floor the orchestrator promotes against can diverge — a correctness-adjacent drift, not just cosmetic.
- **Fix sketch**: Export one `export const activePromoteFloor = () => getPromoteFloor() ?? DEV_POLICY.promoteFloor;` from `devcase-orchestrator.ts` (next to `DEV_POLICY`), or co-locate it in `dev-control.ts` taking the default as a param to avoid an orchestrator import from the store. Replace both sites with the call. Two callers, both in-scope.

## 4. Duplicated "at the review gate" stage predicate in `approve` and `redesign` routes
- **Severity**: Low
- **Category**: duplication
- **File**: `app/api/devcase/lifecycle/[id]/approve/route.ts:42` + `app/api/devcase/lifecycle/[id]/redesign/route.ts:29`
- **Evidence**: `grep "awaiting_approval.*designed|designed.*awaiting_approval"` returns both: approve uses `if (lc.stage === "awaiting_approval" || lc.stage === "designed")`, redesign uses the negated guard `if (lc.stage !== "awaiting_approval" && lc.stage !== "designed")`. Both encode the same "lifecycle is sitting at the human review gate" set; they are the only two writers that gate on it (orchestrator drives these stages but doesn't re-test this pair).
- **Impact**: Low — two sites, but the gate-stage set is a domain concept; if a third reviewable stage is added (or `designed` is split), both routes must change in lockstep or the gate desyncs.
- **Fix sketch**: A tiny shared predicate, e.g. `export const REVIEW_GATE_STAGES = new Set(["awaiting_approval", "designed"]);` (or `isAtReviewGate(stage)`) co-located with the lifecycle stage list in `devcase-orchestrator.ts` (which already owns `STAGES`). Both routes import and test it.

## 5. Self-contained-store `db()` bootstrap repeated in `dev-control.ts` and `dev-outcomes.ts` (cross-context convention — note only)
- **Severity**: Low
- **Category**: duplication
- **File**: `app/_lib/dev-control.ts:7-34` + `app/_lib/dev-outcomes.ts:62-87`
- **Evidence**: Both lazily memoize `_db`, call `ensureDbDir()`, `new Database(DB_PATH)`, `pragma("journal_mode = WAL")`, `pragma("busy_timeout = 5000")`, then `exec(CREATE TABLE IF NOT EXISTS …)`. BUT this is a **project-wide convention, not a context-local smell**: `grep "busy_timeout = 5000"` across `app/_lib` returns **12 files** and `grep "new Database(DB_PATH)"` returns **15** (application-status-store, decision-config-store, group-eval, interview-prep, offers-store, schedule-store, scheduler-store, sim-store, templates-store, rediscovery-alert-store, job-ingest, db-portability, db/core, …). Only 2 of these are in my scope. The pattern is the deliberate "self-contained second connection so the autonomous pipeline's audit log is independent of the main schema" design (see the dev-control.ts:1-6 and dev-outcomes.ts:6-8 docstrings).
- **Impact**: Real but cross-cutting; deduping only the two in-scope copies would create an inconsistent half-measure, and a full consolidation touches ~13 files across many contexts.
- **Fix sketch**: Do **not** fix within this context. Flag for a platform-level pass (Data Layer context): a shared `openSecondaryStore(create: string): () => Database.Database` factory in `db-path.ts`/`db/core.ts` that all self-contained stores reuse. Listed here only so the duplication is on record; deliberately left as a no-op for this scope.
