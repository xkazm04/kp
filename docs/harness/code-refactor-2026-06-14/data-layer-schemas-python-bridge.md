## 3. Verbatim isolated-connection bootstrap duplicated across ~12 stores
- **Severity**: Medium
- **Category**: duplication
- **File**: `app/_lib/db-portability.ts:124-130` (`openForLoad`) + the same idiom in `app/_lib/schedule-store.ts:12-22`, `scheduler-store.ts:23`, `offers-store.ts:19`, `decision-config-store.ts:21-35`, `sim-store.ts:29`, `templates-store.ts:16`, `group-eval.ts:13`, `interview-prep.ts:16`, `dev-control.ts:11`, `dev-outcomes.ts:66`, `rediscovery-alert-store.ts:21`, `job-ingest.ts:19`, `application-status-store.ts:17` (canonical pragmas in `app/_lib/db/core.ts:100-106`)
- **Evidence**: `Grep "new Database\(" app` + `Grep "journal_mode = WAL"` show the SAME memoized-open scaffold copy-pasted ~14×: `let _db = null; function db(){ if(_db) return _db; ensureDbDir(); const d = new Database(DB_PATH); d.pragma("journal_mode = WAL"); d.pragma("busy_timeout = 5000"); d.exec(<CREATE…>); _db = d; return d; }`. Only the CREATE/migration body differs; the open+pragma+memoize wrapper is byte-identical. `db-portability.ts`'s `openForLoad()` repeats the same `new Database(DB_PATH); pragma WAL; pragma busy_timeout=5000` triple a third time. Per kp convention these are intentionally separate connections from `db.ts` (the fork-active singleton) — that is NOT the finding; the finding is the *verbatim wrapper* boilerplate, which `db-path.ts` itself flags as a smell (its header says the `DB_PATH` literal "was previously copy-pasted into a dozen modules… Resolve it once" — exactly this class of duplication, already half-solved via `ensureDbDir`).
- **Impact**: 14 copies of the connection-open contract means a pragma change (e.g. adding `foreign_keys = ON`, raising `busy_timeout`, or a `synchronous` tweak) must be made in 14 places — miss one and that store silently runs different durability/locking semantics. Low bug-risk today, high maintenance drag.
- **Fix sketch**: Add `openStore(): Database.Database` to `app/_lib/db-path.ts` (the existing single-source home, already owning `DB_PATH`/`ensureDbDir`) that does `ensureDbDir(); const d = new Database(DB_PATH); d.pragma("journal_mode = WAL"); d.pragma("busy_timeout = 5000"); return d;`. Each store's `db()` becomes `if (_db) return _db; const d = openStore(); d.exec(<its CREATE>); _db = d; return d;`. `openForLoad()` in `db-portability.ts` collapses to `return openStore();`. SAFE and mechanical — the per-store CREATE/migration bodies (the genuinely distinct logic) stay untouched, and the memoization stays per-module. Do NOT try to also unify the CREATE bodies; only the open wrapper is duplicate. Most of these store files are outside this context's 51-file scope, so a minimal first cut is to land `openStore()` + convert the two in-scope users (`db-portability.ts`, and `core.ts`'s isolated open could optionally adopt it) and migrate the rest opportunistically.

## 4. `safeRowParse` re-implemented as `safeParse`-style inline mappers is consistent, but `core.ts` mixes seed-load + JSON-parse + schema DDL + 4 seeders in one 1098-line file
- **Severity**: Medium
- **Category**: structure
- **File**: `app/_lib/db/core.ts:1-1097`
- **Evidence**: `core.ts` is the de-facto god-module of the data layer: it holds (a) seed-health diagnostics (`SeedIssue`/`recordSeedIssue`/`getSeedHealth`/`loadSeedArray`), (b) the universal `safeRowParse` row-JSON guard imported by ~10 sibling stores, (c) the entire ~400-line `ensureDb()` schema DDL + two migration loops + two guarded unique-index blocks, (d) four seeders (`seedExampleJd`/`seedJobs`/`seedCandidates`/`seedAnalyses`/`seedPipeline`) including an inline ~35-line `SEED_JD_BODY` string literal, and (e) two persisted-row backfills (`migratePipelineStages`, `backfillDeclinedStatus`), plus the `insertWithUniqueSlug`/`prunePromptCache` shared helpers and the `JobRecord`/`PipelineEntry` row types. This is a real cohesion problem — the barrel (`db.ts`) re-exports `./db/core` first precisely because everything else depends on it — but it is a STRUCTURE observation, not dead code, and the split carries migration-ordering risk (the ALTER loops must run after their CREATEs, the seeders after the schema, the prunes after `_db` is assigned), so it is lower-confidence than findings 1-3.
- **Impact**: The schema and the seed data and the row-parse contract all change for different reasons but share one file, so every data-layer PR touches `core.ts` and merge-conflicts concentrate here. The 35-line embedded JD body and 4 seeders also make the schema DDL hard to read at a glance.
- **Fix sketch**: Lowest-risk first step — extract the seeders + their seed constants (`SEED_*_PATH`, `SEED_JD_BODY`, `SEED_*_CREATED_AT`, `seedExampleJd`/`seedJobs`/`seedCandidates`/`seedAnalyses`/`seedPipeline`, `migratePipelineStages`, `backfillDeclinedStatus`) into `app/_lib/db/seed.ts`, exporting a single `runSeeders(db)` that `ensureDb()` calls at the existing call site (preserving exact order). Keep the schema DDL, the migration loops, `safeRowParse`, `insertWithUniqueSlug`, and `prunePromptCache` in `core.ts`. This halves `core.ts` and isolates the seed concern without reordering any boot step. Defer further splitting (DDL vs helpers) — the migration-ordering coupling makes it riskier than it looks, so treat this as a deliberate, test-backed refactor rather than a mechanical move. (Marked Medium/lower-confidence accordingly.)
