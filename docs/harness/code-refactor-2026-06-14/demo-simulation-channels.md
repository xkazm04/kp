## 1. `WaveDecision` type is a drifted local copy of the canonical `ScreenDecision`
- **Severity**: High
- **Category**: duplication
- **File**: `app/features/simulation/SimulationProvider.tsx:16-17` (canonical: `app/_lib/screen-wave.ts:14-30`; sibling copy: `app/features/sub_decisions/ScreenWaveModal.tsx:12-22`)
- **Evidence**: The sim's screen step POSTs `/api/decisions/screen-wave` and consumes `wave.decisions` (SimulationProvider.tsx:457-458). That route returns `ScreenDecision[]` from `runScreenWave` (screen-wave.ts:98, 224). `ScreenDecision` is the documented source of truth and carries `reasonCode: ScreenReasonCode` + `reasonParams` (the locale-renderable mirror of `rationale`, added by DEC4). SimulationProvider re-declares the shape locally as `WaveDecision = { entryId; label; archetype; matchScore; action; rationale }` — dropping `reasonCode`/`reasonParams` — and `SimDecisionWave.tsx` renders the raw English `rationale` only. `grep -rn "ScreenDecision\|WaveDecision" app/` returns exactly three declarations: the canonical `ScreenDecision` (screen-wave.ts), an inline `Decision` type explicitly commented "mirrors ScreenDecision in screen-wave.ts" (ScreenWaveModal.tsx:9-21), and this `WaveDecision`. No file imports `ScreenDecision` for reuse — every consumer re-types the same wire shape by hand.
- **Impact**: Drift risk on a shared contract. The production `ScreenWaveModal` already localizes via `reasonCode`/`reasonParams`; the sim's `SimDecisionWave` silently shows the English-only `rationale`, so a Czech demo shows English rationales here while the real Decisions modal shows Czech. Any future field added to `ScreenDecision` (the comment trail shows this shape has already grown twice) won't reach the sim, and a renamed field fails silently rather than at compile time.
- **Fix sketch**: Export `ScreenDecision` (already exported) and have SimulationProvider import it: `import type { ScreenDecision } from "@/app/_lib/screen-wave"` and define `type ScreenWave = { decisions: ScreenDecision[]; rejected: number; kept: number; cohort: number }`. Delete the local `WaveDecision`. `SimDecisionWave.tsx` already only reads `entryId/label/matchScore/action/rationale`, so it keeps compiling; optionally pass `reasonCode`/`reasonParams` through for localized rationales like the real modal. Also collapse `ScreenWaveModal`'s inline `Decision` onto the same import to retire the third copy.

## 2. Five `/api/sim/*` routes hand-roll the error envelope that `jsonError()` centralizes
- **Severity**: Medium
- **Category**: duplication
- **File**: `app/api/sim/inbound/route.ts:38`, `app/api/sim/reset/route.ts:11`, `app/api/sim/screen-draft/route.ts:26`, `app/api/sim/offer-draft/route.ts:36`, `app/api/sim/offer-link/route.ts:19`
- **Evidence**: `grep -rn "error instanceof Error ? error.message :" app/api/sim` returns all five route catch blocks, each repeating `NextResponse.json({ error: error instanceof Error ? error.message : "…" }, { status: 500 })`. `grep -rn "jsonError\|safeJsonError" app/api/sim` returns no matches — none use the shared helper. `app/_lib/api-response.ts:12` defines `jsonError(err, fallback, status=500)` for exactly this ("hand-rolled in dozens of route files; centralizing it gives every catch block ONE consistent envelope"), and the sibling comms routes in this same context already migrated to `safeJsonError` (`app/api/comms/route.ts:33`, `app/api/comms/[id]/resend/route.ts:36`). The drift is self-documented: `offer-link/route.ts:17` comments "Match the four sibling sim routes' try/catch" — the duplication was copied deliberately rather than factored.
- **Impact**: Five identical ternaries to maintain; any future change to the error envelope (redaction, logging) must touch all five, and the inconsistency with the comms routes' `safeJsonError` means two error styles live in one context.
- **Fix sketch**: Replace each catch body with `return jsonError(error, "Inbound failed.")` (etc.), importing `jsonError` from `@/app/_lib/api-response`. Mechanical, status defaults to 500. These routes return raw business messages (not SQLite/store detail), so `jsonError` is the right helper, not `safeJsonError`.

## 3. Repeated job-scoped cohort selection over `getEntries()` in the sim walk
- **Severity**: Medium
- **Category**: duplication
- **File**: `app/features/simulation/SimulationProvider.tsx:256-258, 391, 415, 428-430` (plus the standalone fetch in `getEntries` at 165-173)
- **Evidence**: The pattern `(await getEntries()).filter((e) => e.jobId === jobId && e.stage === "<Stage>")` (then sometimes `.sort((a,b) => (b.matchScore ?? 0) - (a.matchScore ?? 0))[0]`) appears five times inside one `useCallback` chain: `runGroupEval` (256-258), the source step's "Accepted" poll (391), and the match step's "Accepted" filter + top-"Screened" pick (415, 428-430). Each re-fetches the whole board and re-filters by the same `jobId` closure variable. This is local to the file (not a production-vs-sim drift), confirmed by reading the full `run()`/`runGroupEval()` bodies.
- **Impact**: Low correctness risk but real readability/maintenance cost: the stage strings ("Accepted"/"Screened") and the match-score sort are duplicated, so a stage rename or a "pick top candidate" rule change must be edited in several spots. Already partially mitigated by the `getEntries` throw-on-non-OK guard, so the dedup is purely structural.
- **Fix sketch**: Add two small local helpers inside the provider — `entriesFor(jobId, stage?)` returning the filtered list, and `topScreened(jobId)` returning the highest-`matchScore` Screened entry — and route the five call sites through them. Keeps the best-effort cohort-advance loop (line 420) untouched; purely collapses the filter/sort boilerplate.

## 4. Sim `offer-draft` re-implements salary-band sanitization instead of `normalizeSalaryBand`
- **Severity**: Low
- **Category**: duplication
- **File**: `app/api/sim/offer-draft/route.ts:17-23`
- **Evidence**: The route hand-orders the band: `const lo = band[0] ?? 120000; const hi = band[1] ?? 165000; const min = Math.min(lo, hi); const max = Math.max(lo, hi);` — the exact swap-a-backwards-range logic that `normalizeSalaryBand(min, max)` (`app/_lib/salary-band.ts:73-77`) already provides ("swap a backwards range and reject non-finite/non-positive values"). The comment even narrates the swap reasoning the helper encapsulates. NOTE: the deterministic offer/screen drafts themselves are intentionally NOT shared with the LLM-backed `automation-run.ts` offer path (automation-run.ts:210-213) — that divergence is by design for the keyless demo, so it is correctly NOT flagged as drift; only the inline min/max math overlaps a shared util.
- **Impact**: Minor. A genuinely degenerate stored band (e.g. one element, or `[max, min]`) is handled twice with subtly different fallbacks (the helper returns null → caller fallback; here a missing element silently defaults to a hardcoded 120k/165k). Low blast radius since it is demo-only data.
- **Fix sketch**: `const [min, max] = normalizeSalaryBand(band[0], band[1]) ?? [120000, 165000];` then `const recommended = Math.round((min + max) / 2)`. Removes the four lines of ad-hoc ordering and routes through the tested util. Keep the demo fallback numbers.
