## 1. Duplicated per-reject fairness-downgrade + alert-append logic across the dry-run and commit loops
- **Severity**: Medium
- **Category**: duplication
- **File**: `app/_lib/automation-pass.ts:191-214` (dry-run loop) and `app/_lib/automation-pass.ts:216-282` (commit loop)
- **Evidence**: `executeAutomationPass` runs two near-identical decision loops. Both call `assertAutoRejectFair(byId.get(d.entryId))` and, on `!verdict.allowed`, perform the SAME three-step downgrade: set `d.action = "hold"`, rewrite `d.reason` to a "fairness backstop refused… Original policy decision:" string, and append the alert with the identical idempotent guard:
  ```ts
  d.alerts = (d.alerts ?? []).includes(FAIRNESS_BLOCKED_REJECT_ALERT)
    ? d.alerts
    : [...(d.alerts ?? []), FAIRNESS_BLOCKED_REJECT_ALERT];
  ```
  Verified literally duplicated: `grep FAIRNESS_BLOCKED_REJECT_ALERT` returns exactly two append sites (lines 203-205 and 259-261), and `grep assertAutoRejectFair` returns exactly two call sites in this file (lines 197, 242). The dry-run "advance/reject/hold → summary++" counting (192-211) is also a structural mirror of the commit loop's summary increments. The two loops legitimately differ only in their *side effects* (dry-run annotates; commit calls `actOnPipelineEntry` + `dispatchRejection` + records events), which is the intentional AUTO3 split — but the fairness verdict→downgrade→alert decision is pure and identical.
- **Impact**: The fairness backstop is the spec-pinned safety invariant (docs/AUTOMATION_SPEC.md §risks). Having its refusal/downgrade encoded twice means a future change to the refusal message, the alert shape, or the summary accounting must be applied in two places or the preview silently stops matching what the commit enforces — exactly the "preview must show the verdict the commit would enforce" guarantee the comments insist on.
- **Fix sketch**: Extract a pure helper, e.g. `applyFairnessVerdict(d: AutomationDecision, verdict: AutoRejectVerdict, summary: AutomationSummary): boolean` (or `downgradeRejectToHold(d)`), that mutates the decision (action→hold, reason, deduped alert) and bumps `summary.held`, returning whether the reject was refused. Both loops call it before their branch-specific side effects; the commit loop additionally proceeds to `actOnPipelineEntry`/`dispatchRejection` only when the verdict was allowed. No new tests required to land (no test pins `executeAutomationPass` internals — confirmed `app/_lib/` has no `automation-pass.test.ts`), but `automation-fairness.test.ts` continues to pin the verdict logic.

## 2. Optimistic-CAS stale-stage no-op pattern duplicated across the pass and the per-task screen path
- **Severity**: Medium
- **Category**: duplication
- **File**: `app/_lib/automation-pass.ts:229-236` and `app/_lib/automation-pass.ts:244-253` (advance + reject), mirrored in `app/_lib/automation-run.ts:193-199` (screen advance)
- **Evidence**: Three sites repeat the same idiom: call `actOnPipelineEntry(id, action, undefined, { expectedStage: snapshotStage })`, and on a falsy result treat it as "stage changed mid-pass → skip the move and any dependent event," rewriting the decision/result to a `skipped`/`none` outcome. In `automation-pass.ts` advance (230-235) and reject (244-253) both implement this; `automation-run.ts` screen (194-199) implements the same CAS-failed → `skipped_stage_changed` early-return. The comments at both files explicitly cross-reference each other ("mirrors the policy-pass hardening (automation-pass.ts)"), confirming the intentional shared contract is hand-mirrored rather than shared in code.
- **Impact**: Low-to-moderate maintenance risk: the CAS-on-snapshot-stage hardening (idea-b6310b92) is security/correctness-relevant (prevents acting on a stage a recruiter moved during the Python hop). A future change to how a stale apply is signalled would need touching all three sites. This is genuine duplication but the surrounding side effects differ enough that a full extraction is less clean than finding 1.
- **Fix sketch**: Lower-confidence than #1 — the call shape is already a one-liner via `actOnPipelineEntry`'s `expectedStage` option, so the duplication is mostly the *handling* of the falsy return. A small helper like `appliedOrStale(entryId, action, snapshotStage)` returning a discriminated `{applied:true}|{applied:false}` could centralize the "skip dependent effects on stale" decision, but verify it reads cleanly at all three call sites before consolidating; if it forces awkward branching, leave as-is (the mirror is intentional and documented). Recommend pairing with #1 or deferring.

- **Impact**: Minor confusion/dead entry: a reader expects `DRAFT_EVENT` to be authoritative for outreach's event kind, but the live outreach branch records `outreach_sent` (via `dispatchOutreach`/`comms-dispatch.ts`), never `outreach_drafted`. The unreachable key invites a wrong edit.
- **Fix sketch**: Remove the unreachable `outreach: "outreach_drafted"` entry from `DRAFT_EVENT` (only `rejection` and `prep` reach the fallback). Optionally add a one-line comment that `DRAFT_EVENT` covers only the tasks that fall through to the generic draft branch. No behavior change. Confirm with `grep "outreach_drafted"` (no other consumer) before removing.
