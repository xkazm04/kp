## 1. Consolidate the duplicated `available()` (resolve-key → import-SDK) across the three direct adapters
- **Severity**: Medium
- **Category**: duplication
- **File**: `pipeline/jobfit/llm/adapters/anthropic_api.py:25-32`, `pipeline/jobfit/llm/adapters/openai_api.py:21-28`, `pipeline/jobfit/llm/adapters/gemini_api.py:26-33` (base: `pipeline/jobfit/llm/base.py:143-144`)
- **Evidence**: The three adapters carry the same `available()` body — `if not self._resolved_key(): return False` → `try: import <sdk> except ImportError: return False` → `return True` — differing only in the import target (`anthropic`, `openai`, `from google import genai`). `_resolved_key()` is likewise near-identical: `self.api_key or os.getenv(<KEY>)`, where OpenAI already factored its env name into a class attr `_env_key = "OPENAI_API_KEY"` (azure inherits it as `"AZURE_OPENAI_API_KEY"`) but Anthropic hardcodes `"ANTHROPIC_API_KEY"` inline and Gemini hardcodes the `GEMINI_API_KEY`/`GOOGLE_API_KEY` pair inline. Grep for the surface (`_resolved_key|_env_key|_make_client|available`) over `C:\Users\mkdol\dolla\kp` shows the only external touch point is `tests/test_llm_base.py`, which patches `_make_client` and asserts `available()` returns False without a key — both behaviors a base implementation preserves. The base class (`base.py:143`) currently only declares `available()` as `raise NotImplementedError`.
- **Impact**: Four near-copies of the key/SDK-availability dance; adding the next adapter (or a 5th provider) means re-typing the same two-branch boilerplate, and the inline-vs-`_env_key` inconsistency is exactly the kind of drift that lets one adapter silently diverge (e.g. forgetting `load_local_env()`).
- **Fix sketch**: Give `TextProvider` a default `available()` plus a small contract for the two varying bits: a class attr `_env_keys: tuple[str, ...]` (anthropic `("ANTHROPIC_API_KEY",)`, openai `("OPENAI_API_KEY",)`, gemini `("GEMINI_API_KEY","GOOGLE_API_KEY")`, azure `("AZURE_OPENAI_API_KEY",)`) and a `_import_sdk()` hook (or a `_sdk_module = "anthropic"` string the base imports). Base `_resolved_key()` becomes `self.api_key or first-set env over self._env_keys` (after `load_local_env()`); base `available()` becomes resolve-key + `_import_sdk()`. Delete `_resolved_key`/`available` from anthropic, openai, gemini; keep azure's `available()` override (it ANDs the endpoint check, calling `super().available()`). Keep each adapter's `_make_client`/`_call` as-is — those are genuinely provider-specific (see finding #2). Tests in `test_llm_base.py` continue to pass unchanged.

## 2. `_make_client` is structurally repeated but only marginally dedup-able — leave the per-SDK bodies, factor only the shared `max_retries=0` intent
- **Severity**: Low
- **Category**: duplication
- **File**: `pipeline/jobfit/llm/adapters/anthropic_api.py:34-41`, `pipeline/jobfit/llm/adapters/openai_api.py:30-36`, `pipeline/jobfit/llm/adapters/azure_openai.py:50-59`
- **Evidence**: All three `_make_client` constructors pass `api_key=self._resolved_key(), timeout=float(timeout), max_retries=0`, and anthropic + openai carry the identical comment "max_retries=0: TextProvider.complete owns the retry policy." The constructors instantiate different SDK clients (`anthropic.Anthropic`, `openai.OpenAI`, `openai.AzureOpenAI`), so the bodies cannot be merged without an indirection that would obscure more than it saves. Confirmed each adapter's `_make_client` is called only from its own `_call`/`available` (grep `_make_client` over the repo: only the three adapters + a `mock.patch.object(..., "_make_client")` in `test_llm_base.py`).
- **Impact**: Low — the only true duplication here is the `max_retries=0` rationale comment, repeated twice; the bodies legitimately differ.
- **Fix sketch**: Do NOT force a shared `_make_client`. The safe, minimal move is to drop the duplicated rationale comment to a single sentence in the `TextProvider.complete` docstring (which already owns retries, `base.py:151`) and leave a one-word `# max_retries=0` at each call. This is a note to prevent a future over-eager "DRY the clients" refactor; flagging it explicitly so the boundary is documented rather than re-litigated.

## 3. Redundant invocation-example docstring duplicated between `bench/__init__.py` and `bench_cli.py`

- **Category**: cleanup
- **File**: `pipeline/jobfit/llm/bench/__init__.py:9-20`, `pipeline/jobfit/llm/bench/bench_cli.py:1-14` (also mirrored in `docs/LLM_PROVIDER_LAYER.md:47-52`)

- **Impact**: Low — purely a maintenance/drift cost: three copies of the same example command means a flag rename (e.g. `--include-payloads`) must be updated in three spots, and they can silently diverge (the `__init__` copy already omits `--lang en` that `bench_cli.py` includes).

Keep the full runnable example in exactly one place — `bench_cli.py` (closest to `argparse`), since that is where a reader looks for flags. No code changes, no `__all__` change.

## 4. `USE_CASE_REQUIREMENTS` json-only rows are documentation-only redundancy (intentional — keep, but note)
- **Severity**: Low
- **Category**: cleanup
- **File**: `pipeline/jobfit/llm/capabilities.py:27-49`
- **Evidence**: Of the 21 `USE_CASE_REQUIREMENTS` rows, 19 map to the identical `frozenset({CAP_JSON})`; only `cv_analysis` and `profile_extract` differ (`{CAP_FILE_INPUT}`). `unsupported_caps` (line 74-77) already defaults unknown use cases to `frozenset({CAP_JSON})`, so the 19 json-only rows are behaviorally equivalent to having no row at all. The module docstring (lines 24-26) states this is deliberate: the rows exist "to (a) gate multimodal/grounded cases and (b) document the set." I verified the registry path (`registry.py:40` `unsupported_caps`) is the only consumer, and the json-only rows never change its result vs the default.
- **Impact**: Low — no bug; the table is longer than it strictly needs to be, and every new json-only use case adds a no-op row. Per kp conventions, this "documents the catalog" and the gating rows (`cv_analysis`, `profile_extract`) are load-bearing, so it should NOT be force-trimmed.
- **Fix sketch**: Recommended action is to LEAVE AS-IS (documenting the call-site catalog has real value and matches the stated design). If a future cleanup wants to shrink it, the only safe move is to keep the two capability-gating rows and replace the 19 json-only entries with a short comment listing the known json use cases — but this trades self-documentation for brevity and is not worth a behavior-neutral churn now. Flagged for completeness only.
