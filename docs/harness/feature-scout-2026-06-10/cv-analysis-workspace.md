## 1. Finish CV1's deferral: thread the saved-analysis slug into the live result (Add to pipeline + stable report link on the Analyze tab)
- **Value**: High
- **Category**: functionality
- **Effort**: S
- **Where**: `app/features/sub_analyze/AnalyzeApi.ts:98` (zod parse drops the slug) (+ `app/_lib/analyze-run.ts:173,188` attaches `persistence`, `app/_lib/schemas.ts:69` `analysisSchema`, `app/features/sub_analyze/AnalyzeTab.tsx:47-61` renders `ResultPanel` without `pipelineRef`, `app/history/[slug]/page.tsx:85-97` the working pattern)
- **Gap**: This is the **documented unshipped deferral** from the 2026-06-08 campaign (`harness-learnings.md:73`, `FIXES-WAVE-1.md:81`) — verified still open. `runAnalyze` returns `{ ...analysis, persistence: { slug } }` in the task result, but `watchAnalysis` parses it with `analysisSchema` (a zod object — unknown keys stripped), so the client never sees the slug; `AnalyzeTab` therefore can't build a `PipelineRef`, and the live result also has "no stable URL to share" (the explicit reason `ReportActions` was scoped to history in `FIXES-WAVE-3.md:37`). The deferral note feared crossing the `schemas.generated.ts` boundary, but `comparison` already proves the safe pattern: a TS-side `.extend` on the generated schema.
- **Proposal**: Extend `analysisSchema` (or a watch-only wrapper) with `persistence: z.object({ slug: z.string() }).nullish()` — TS-side, exactly like `comparison`; surface `savedSlug` through `onResult` into `useAnalyzeForm`'s result state. In `AnalyzeTab`, when `savedSlug && selectedJdSlug` (the client already holds the JD slug at submit), pass the same `pipelineRef` the history page builds (`candidateId: savedSlug, jobId: jd_slug, …`), and add a "View saved report" link / `ReportActions` to `/history/<savedSlug>`. This also unblocks two sibling 2026-06-10 findings (`github-code-analysis.md` #1/#2), whose PATCH-attach flow presupposes the slug being client-side.
- **Why users need it**: The primary intake surface still dead-ends at the moment of highest intent — the recruiter must navigate to History and re-find the run they just watched finish to act on it or share it.

## 2. Label saved analyses with the extracted candidate name, not the CV filename
- **Value**: Medium
- **Category**: user_benefit
- **Effort**: S
- **Where**: `app/_lib/analyze-run.ts:194` (`persistAnalysis(candidateLabel, …)` receives the file label) (+ `app/api/analyze/route.ts:124` `label = file.name`, `app/_lib/analyze-run.ts:179` `"${winner.label} (best of N)"`, `app/_components/results/extraction/ExtractionTab.tsx:17` the only surface showing the real name, `app/features/sub_history/HistoryTab.tsx:186`, `app/history/[slug]/page.tsx:89`)
- **Gap**: The Gemini extraction already returns the candidate's real name (`pipeline/jobfit/gemini.py:31` `"name": "candidate name or null"`; `candidate.name` in `schemas.generated.ts:9`), but the persisted `candidate_label` is always the upload's filename. So History rows, the history search (RES3 matches on `candidate_label`), the multi-variant winner label, and — via the history page's add-to-pipeline — pipeline entries and comms recipient resolution (label fallback in `comms-dispatch.ts`) are all keyed to strings like `cv_final_v3.pdf` while the human name sits unused in the same payload. Missed by the prior scout; the shipped surfaces (history search, add-to-pipeline, dedup work) have since raised its cost.
- **Proposal**: In `persistAnalysis`, prefer a non-empty trimmed `analysis.candidate?.name` for `candidateLabel`, falling back to the file label (and keep the filename available in the payload it already lives in); the multi-variant path becomes `"<Name> (best of N)"`. Downstream surfaces (history list/detail, pipeline add, comms label fallback) inherit the fix with zero changes. Optionally show "from <filename>" as secondary text on the history detail header.
- **Why users need it**: Recruiters scan history and the board by people, not by upload artifacts — "novak-cv-2024-final(2).pdf" defeats the just-shipped history search and leaks into candidate-facing pipeline records.

## 3. Per-run report language override (en/cs) on the Analyze form
- **Value**: Medium
- **Category**: feature
- **Effort**: S
- **Where**: `app/api/analyze/route.ts:84` (`lang = await getServerLocale()` — cookie only) (+ `app/features/sub_analyze/AnalyzeForm.tsx` (no language control; zero `lang|locale` hits in `sub_analyze/`), `app/_lib/analyze-run.ts:43` `--lang` already wired, `app/_lib/cache.ts` lang-keyed cache key, `app/_components/LanguageSwitcher.tsx`)
- **Gap**: Opened by the new i18n layer (7922fbe): the analysis narrative language is silently inherited from the UI locale, with no per-run choice. A cs-locale recruiter who needs the English report for an international hiring panel (reports are now shared artifacts — W3's print/PDF + copy-link) must flip the entire app language via the global `LanguageSwitcher` and re-run. All the plumbing for an override already exists: the route forwards `--lang` per request and the analyze cache is lang-keyed, so the same CV re-run in the other language is already cache-correct. (Distinct from sibling 2026-06-10 lang findings, which add missing lang support to the JD builder / dev-case / comms paths; here the support exists and only the control is missing.)
- **Proposal**: Add a small "Report language" select (en/cs) beside the Analyze button, defaulting to the active locale; append it to the submit `FormData`, and in the route prefer the validated field (`isLocale`) over `getServerLocale()`. Optionally record the run's lang in the saved payload metadata and badge it on history rows so a recruiter knows which language a stored report is in.
- **Why users need it**: Czech-market recruiting routinely mixes Czech recruiters with English-speaking hiring managers (and vice versa); the report's language should follow its audience, not the operator's UI chrome.
