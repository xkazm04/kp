## 1. Give roles a terminal lifecycle — close/fill a published role
- **Value**: High
- **Category**: functionality
- **Effort**: M
- **Where**: `app/_lib/job-ingest.ts:112` (`setJobStatus(jobId, status: "draft" | "published")` — the whole state machine), `app/api/jobs/[id]/publish/route.ts:24` (only forward transition), `app/apply/[id]/page.tsx:13-14` (apply gated only on `getJob` existence), `app/_lib/db.ts:959` (`listJobs` has no status dimension), `app/features/sub_jobs/JobPostingModal.tsx:32` (apply link copyable for any job, drafts included)
- **Gap**: The job lifecycle is one-way and never terminal: NULL (seeded/live) → draft → published, full stop. There is no close/filled/archived state, no route or UI to retire a role, and `/apply/[id]` accepts applications for any existing job forever (including never-published drafts). Meanwhile pipeline entries have a rich terminal vocabulary (`rejected`, `declined`, `rematched`, Hired stage — `db.ts:3335` `rematchSourceEntry`), so the candidate side can finish but the role side cannot. A filled role keeps its apply link live, keeps appearing as an open role in the catalog, and keeps being ranked against the full candidate pool in sourcing/rediscovery/matrix runs.
- **Proposal**: Extend the status union with `closed` (optionally `filled` when the close follows a Hired entry), add `POST /api/jobs/[id]/close` (idempotent, mirror of publish), and a "Close role" action on the posting modal footer. Gate `/apply/[id]` to published-only (closed → a friendly "this role has been filled" page); badge closed rows in `JobsTable` and default the catalog filter to open roles. Optionally let close offer "rematch active pipeline entries to other open roles" via the existing rematch machinery.
- **Why users need it**: A recruiting catalog where roles can only ever open is a one-way ratchet — recruiters end up sourcing, ranking and accepting applications against positions that were filled weeks ago, and the public apply link silently collects candidates nobody will ever process.

## 2. Persist sourcing state on the candidate ranking — show "in pipeline / reached out" across sessions
- **Value**: High
- **Category**: user_benefit
- **Effort**: M
- **Where**: `app/_lib/useReachOut.ts:14-16` and `app/_lib/useAddToPipeline.ts` (per-candidate `Set`s in component state — session-only), `app/features/sub_jobs/RecruiterCandidates.tsx:35-36` (consumes only those hooks), `app/api/jobs/[id]/candidates/route.ts:57` (returns the ranker rows untouched — no pipeline/outreach decoration)
- **Gap**: New seam opened by shipping JOB3 (W2): "Reach out" and "+ pipeline" now exist on the ranking, but their state lives only in the hooks' in-memory `Set`s. Reopen the role tomorrow and every candidate — including ones already filed into this job's pipeline or already sent a first-touch — shows fresh, active buttons with zero indication of prior contact. The durable truth exists server-side: pipeline entries are keyed by `jobId`+`candidateId`, and outreach writes a per-entry `outreach_sent` event (`app/_lib/comms-dispatch.ts:61`); rediscovery even uses it implicitly (`rediscover/route.ts:96` excludes `activeHere`), but the main candidates tab never reads it.
- **Proposal**: Decorate each ranked row in `/api/jobs/[id]/candidates` with `{ inPipeline: stage|null, outreachSent: boolean }` by joining the job's pipeline entries + `outreach_sent` events (one query each, keyed by candidateId). In `CandidateCard`, render the persisted state the same way the optimistic hooks already do ("✓ Reached out" / "In pipeline · Screened" badges instead of buttons), keeping the hooks for in-session optimism.
- **Why users need it**: "Who have I already contacted for this role?" is the basic memory of a sourcing tool; today the answer survives only until the modal closes, so recruiters re-click (harmless but misleading — the idempotent server quietly no-ops while the UI implies a fresh outreach went out).

## 3. Localize the publish-ready posting markdown (the i18n hole left in a candidate-facing artifact)
- **Value**: Medium
- **Category**: feature
- **Effort**: S
- **Where**: `app/features/sub_jobs/jobMarkdown.ts:8-61` (hardcoded "About the role", "What you'll bring", "Nice to have", "Details", "Early-career welcome", "Salary:", "+ years", "level"; line 46 uses raw English `FAMILY_LABEL`, bypassing `useEnumLabel`), `app/features/sub_jobs/JobPostingModal.tsx:26` (renders + copies it)
- **Gap**: Opened by the i18n commit (7922fbe). Every surface around the posting is now bilingual — the modal chrome (`jobs.posting` keys), the apply script (`buildApplyScript(job, t)` in `app/apply/[id]/page.tsx:22`), enum labels — except the posting document itself, the one artifact explicitly designed to be copied out to a job board. Its salary line is already formatted `cs-CZ`/CZK (`jobMarkdown.ts:4` — this is a Czech-market corpus), yet a recruiter working in Czech copies a posting scaffolded in English.
- **Proposal**: `jobToMarkdown(job, strings)` — keep it a pure function, pass a heading/label table resolved from the active locale (next-intl `useTranslations("jobs.markdown")`), and route the Field line through the same enum-label catalog as the table. Add a small EN/CS toggle on the Posting tab so the posting language can differ from the app locale (recruiter runs the app in EN, posts to a Czech board) — the toggle just swaps the strings table for the memoized render and the copy action.
- **Why users need it**: The copy-markdown action is the product's external output; after full bilingual i18n, an English-only posting for CZK-salaried Czech roles is the most visible remaining seam, and hand-translating headings on every paste defeats the "publish-ready" promise.

## 4. Disclose the not-eligible cohort with its KO reasons (ranker output that never reaches this UI)
- **Value**: Low
- **Category**: user_benefit
- **Effort**: S
- **Where**: `pipeline/jobfit/recruiter.py:62` (`koReasons` emitted per candidate), `app/features/sub_jobs/JobsTypes.ts:96` (typed on `CandRow`), `app/features/sub_jobs/RecruiterCandidates.tsx:97-112` (KO-failed rows filtered out; rendered only as a "N not eligible" count)
- **Gap**: `rank_candidates_for_job` ships per-candidate KO reasons in every `/api/jobs/[id]/candidates` payload, but the recruiter view discards the entire not-eligible cohort behind a count — the recruiter can't see whether "12 not eligible" means everyone lacks German or everyone is one year short. NOT the retired JOB4 (that was aggregate analytics — eligible/KO counts, score histogram, sourced totals); this is the qualitative per-candidate disclosure, with an existing precedent on the Match surface (`MatchShared.tsx:200-257` `KoReasonsNote`).
- **Proposal**: A collapsed "Not eligible (N)" section under the two columns listing each KO'd candidate with their `koReasons` strings (data already on the client — zero server change). Near-misses (single KO reason) could sort first, since they're the ones a recruiter might rescue by relaxing a must-have on the JD.
- **Why users need it**: When a role sources thin, the fix depends on *why* the pool fails — a visible KO breakdown turns "only 3 eligible" from a dead end into an actionable JD edit.
