# Feature Scout — Dev Case Python Engine (2026-06-10)

> Total: 6 (3H/2M/1L)

## 1. Turn the blind one-click approval into a real review — show, edit, and regenerate the designed case at the human gate
- **Value**: High
- **Category**: functionality
- **Effort**: M
- **Where**: `app/features/sub_dev/LifecycleRow.tsx:28` (+ `app/api/devcase/lifecycle/[id]/approve/route.ts:14`, `pipeline/jobfit/devcase/design.py:180` (`design_case` takes no feedback/revision input), `app/_lib/devcase-orchestrator.ts:97`, `app/features/sub_dev/DevTypes.ts:91` (`Lifecycle` drops role/case/analysis))
- **Gap**: When `gateApproval` routes a flagged design to a human (`awaiting_approval`), the recruiter sees one detail line ("3 stated-vs-real gaps — human review") and an Approve button — the designed role, case, probes and the analysis that flagged it are persisted on the lifecycle record (the GET serves full rows) but the UI type drops them. No edit, no regenerate: `DEV_EXTENSION_PLAN.md` §2 explicitly promised "recruiter reviews/**edits**/approves". The engine likewise has no seam to take reviewer feedback into a redesign.
- **Proposal**: Expand an `awaiting_approval` row into a review drawer: the analysis (gaps/risks/confidence), the candidate-safe `caseToMarkdown` preview, and the internal probe panel (all data already server-side). Allow inline edits of title/brief/tasks/timeboxHours + rubric weights (per-case `rubricDimensions` already round-trip — `evaluate._ordered_dimensions` prefers the case's own weights, so a lead-role judgment-heavy rubric works today with zero engine change). Add a `--feedback` arg to `devcase_cli design-artifacts` appended to the design prompt so "Regenerate with note" produces a revised case; Approve persists the (possibly edited) artifacts via the existing `approveLifecycleCase`. Covers the D3-findings "anchor choice / timebox override / rubric weights" UI levers in one surface.
- **Why users need it**: The human gate is the system's central oversight claim, and today it asks a recruiter to sign off on an assignment they cannot see, let alone fix — every flawed design forces a full re-run from intake.

## 2. Close the CV→probe loop: wire the dark `design_case(focus_probes=…)` bridge
- **Value**: High
- **Category**: feature
- **Effort**: M
- **Where**: `pipeline/jobfit/devcase/design.py:186` (+ `pipeline/jobfit/soft_signals.py:291` `panel_to_probe_briefs`, `pipeline/jobfit/devcase/devcase_cli.py:346` (design-artifacts never passes it), `app/_lib/devcase-run.ts:95`)
- **Gap**: `design_case` fully implements targeted covert probes from CV hypotheses — the LLM prompt's "TARGETED CONFIRMATION" block AND deterministic `t<i>` probes — and `soft_signals.panel_to_probe_briefs` (the "Rec B bridge") converts a candidate's antipattern panel into exactly the `{kind, focus, rationale}` briefs it consumes. But the whole `soft_signals` module has **zero production importers** (tests only), and no CLI flag or TS caller ever passes `focus_probes`. The headline capability — an exercise that covertly verifies a specific over-claimed skill — is unreachable.
- **Proposal**: Add `--focus-probes-json` to `devcase_cli design-artifacts` and a small `soft-signal-panel` command (profile JSON → `build_soft_signal_panel` → panel + briefs, deterministic — no provider needed). On the TS side, offer "Design a take-home for this candidate" from a saved profile (or accept an optional target-candidate ref on the need intake): build the briefs, pass them through `runDesignArtifacts`, store `targetCandidateRef` on the case, and badge the targeted probes in CaseDetail's internal panel ("verifies CV claim: …").
- **Why users need it**: This is the engine's differentiated promise — the take-home stops being generic and starts confirming the exact claims the CV made that the recruiter doubts; the entire confirmation machinery is already built and tested, only the last wire is missing.

## 3. Read the DECISIONS log the case forces every candidate to keep
- **Value**: High
- **Category**: functionality
- **Effort**: M
- **Where**: `pipeline/jobfit/devcase/reflect.py:94` (`_context` — commit messages + tree names only) (+ `pipeline/jobfit/devcase/evaluate.py:271` `mint_followups`, `pipeline/jobfit/devcase/seed_materializer.py:33` (`DECISIONS.md` shipped in every seed), `app/_lib/repo-snapshot.ts:162` (`fetchRepoSignals` fetches no file contents), `app/_lib/devcase-run.ts:479` (`decisionsLogPresent` = filename regex))
- **Gap**: Case-design v4's authorship contract treats the submission as "a record of decisions": the seed ships a `DECISIONS.md` template, a case task mandates keeping it, and `mint_followups` claims to anchor questions to "which defensible option they shipped". But the evaluator never reads the record — `fetchRepoSignals` pulls commit subject-lines and top-level file NAMES only, so reflection, probe outcomes and followups are inferred from 140-char commit messages; the candidate's actual stated decisions and rejected alternatives never reach a single prompt. The TS side checks only that a file matching `/decision/i` exists.
- **Proposal**: Fetch `DECISIONS.md` content (plus, capped, files named by probe `where`s) in `fetchRepoSignals` — one extra contents call, head+tail truncated per the repo's trust-critical truncation convention. Thread it into `reflect._context` and `mint_followups`' ctx so `assess_tooling` can judge probe outcomes against the candidate's own log (classify which `decisionSpace` option was shipped) and followups can quote it ("you wrote you rejected X — why?"). Keep the hedging invariant: the log is itself possibly LLM-written, which is precisely why followups should quote it live.
- **Why users need it**: The decisions log is the one artifact the whole v4 design exists to extract, and today it is write-only — evaluations and authorship questions rest on commit one-liners while the richest signal sits unread in the repo.

## 4. Surface the engine's fairness/discrimination gates in the app (engine health card)
- **Value**: Medium
- **Category**: feature
- **Effort**: M
- **Where**: `pipeline/jobfit/devcase/submission_eval.py:455` (+ `pipeline/jobfit/devcase/lifecycle_eval.py:215`, `pipeline/jobfit/devcase/lifecycle_audits.py:75`, `app/control/page.tsx` (the designated oversight surface), `app/_lib/tasks.ts`)
- **Gap**: The fairness gate (AI use never penalised, verification rewarded), the discrimination gate (the AI-no-verify "gamer" caught) and role-fit audits are the subsystem's defensibility story — and they are **CLI-only**: no route, task kind, or UI ever runs `lifecycle_eval`/`submission_eval` (grep: importers are docs/README only). An operator who changes prompt versions, swaps providers, or tunes the promote floor has no in-app way to see whether the evaluator currently passes its own gates, or whether the LLM path is silently error-falling-back (the dangerous false-green W5 documented).
- **Proposal**: A `devcase_eval` background-task kind running `python -m …submission_eval --count 24 --json` (plus an optional `lifecycle_eval --no-llm` health pass), persisting the signals JSON. An "Engine health" card on `/control`: per-gate badges (pass / fail / inconclusive / not_evaluable — the tri-states already exist), an `error_fallbacks > 0` degraded-provider warning, prompt versions, last-run timestamp, and a re-run button (audited via `recordAudit`).
- **Why users need it**: A high-risk automated hiring evaluator should show its operator that it is currently fair and discriminating — today that proof exists but only a developer with a terminal can see it.

## 5. Generate candidate-facing case artifacts in the candidate's language (en/cs)
- **Value**: Medium
- **Category**: user_benefit
- **Effort**: S
- **Where**: `pipeline/jobfit/devcase/interview_scenario.py:189` (`lang` param exists but `devcase_cli.py:267` never passes it — dead seam) (+ `pipeline/jobfit/devcase/design.py:180`, `pipeline/jobfit/devcase/seed_materializer.py:176` (no lang at all), `pipeline/jobfit/i18n.py:47`)
- **Gap**: The app just went fully bilingual (commit 7922fbe) and this run's sibling scouts propose a bilingual candidate apply page — but everything that page would render is generated English-only: the case brief/tasks, the seed's README + DECISIONS.md, and the spoken interview narration. `scenario_from_case` already accepts `lang` ("en | cs") and builds the `language_directive` prompt suffix, yet no caller can reach it.
- **Proposal**: Add `--lang` to `design-artifacts`, `materialize-seed` and `interview-scenario` (append `language_directive(lang)` exactly as `group_compare`/`match_reasoning` do); a language selector on the need intake persisted on the lifecycle/case and threaded by `devcase-run.ts`/the orchestrator. Deterministic fallbacks stay English, documented — same contract `interview_scenario` already states. (Distinct from archived VOX5: that was the voice runtime's per-role language; this is the devcase engine's own existing-but-unreachable seam producing the artifact CONTENT.)
- **Why users need it**: A Czech junior receiving an English take-home + English voice-screen narration undercuts the new bilingual candidate experience; the engine is one flag away from fixing it.

## 6. Render the persisted process trace (decisions-log kept, cadence) on the evaluation panel
- **Value**: Low
- **Category**: user_benefit
- **Effort**: S
- **Where**: `app/_lib/devcase-run.ts:404` (`processTrace` persisted on every bundle) (+ `app/features/sub_dev/DevTypes.ts:135` (`EvalBundle` omits it), `app/features/sub_dev/EvalPanel.tsx:98`)
- **Gap**: Every saved evaluation bundle carries deterministic telemetry — `commitCount`, `cadence {spanHours, bursty}`, `decisionsLogPresent` — persisted explicitly "so the decisions-log contract is checkable later instead of taken on faith". It is checkable by no one: the field is missing from the `EvalBundle` type and never rendered.
- **Proposal**: Add `processTrace` to `EvalBundle` and a small strip in EvalPanel's trace section: a "DECISIONS log: kept / missing" badge (coral when missing — keeping it is a mandated task of the case), and "N commits over X h" with a neutral "single sitting" chip when `bursty` (the code is explicit this is a how-they-worked signal, not a verdict — keep that framing).
- **Why users need it**: Whether the candidate honored the decisions-log contract and how the work was paced are exactly the cheap, factual context a reviewer wants beside the LLM's interpretation — it is already computed and stored on every row.
