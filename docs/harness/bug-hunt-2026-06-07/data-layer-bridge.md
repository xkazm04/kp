## 1. Canceling a task never kills the spawned Python child — leaked/zombie process keeps burning the LLM budget
- **Severity**: High
- **Category**: resource-leak
- **File**: app/_lib/tasks.ts:232-247 (controller) + app/_lib/reasoning-run.ts:46, app/_lib/analyze-run.ts:97, app/_lib/group-eval-run.ts:181,231, app/_lib/devcase-run.ts:76+, app/_lib/jd-build-run.ts:40, app/_lib/automation-run.ts:130
- **Scenario**: A recruiter starts an `analyze` / `group_eval` / `reasoning` task (each spawns a long-running `python -m …` process that calls Gemini/Claude). They hit Cancel (DELETE /api/tasks/[id]). `cancelTask` calls `controller.abort()`, `runOne`'s `await spec.run(...)` is *not* interrupted (the handler isn't listening to the signal), the task row is eventually finished as "canceled", but the Python subprocess keeps running to completion — making a full, billable LLM call whose result is then thrown away.
- **Root cause**: `spawnPython` fully supports `opts.signal` (python-runner.ts:183-187 wires `abort → SIGKILL`), and `runOne` passes `controller.signal` into the handler's `ctx`. But **every** background-task handler calls `spawnPython(args)` with no second argument (the lone exception is job-ingest.ts:156, which is not a task handler). The `child` handle is destructured away and discarded, and `ctx.signal` is never threaded into the spawn. So the abort path that exists in the runner is dead code for the actual workloads.
- **Impact**: Cancel is a lie for the most expensive operations. Orphaned `python`/`claude` processes accumulate under repeated cancel/retry, each consuming a Claude-subscription slot (the very thing `MAX_CONCURRENT = 2` exists to protect) and real API/subscription cost, while the slot accounting in `runOne` has already been freed for a *new* run. Under a few cancel-and-retry cycles you can have many more live children than `MAX_CONCURRENT`.
- **Fix sketch**: Thread `ctx.signal` through every handler into `spawnPython(args, { signal: ctx.signal })`. Minimal change: have each `run*` function accept an optional `AbortSignal` and forward it; in `tasks.ts` the handlers already receive `ctx.signal`. Optionally also pass a per-kind `timeoutMs`. This makes the existing kill path live.

## 2. `runAnalyze` parses raw `JSON.parse(stdout)` instead of `parsePythonJson`, 502-ing successful paid analyses on trailing interpreter chatter
- **Severity**: High
- **Category**: silent-failure
- **File**: app/_lib/analyze-run.ts:104-110
- **Scenario**: The analyze CLI (`pipeline.jobfit.cli`) runs a real multimodal LLM analysis. The interpreter (or an async provider client) prints a shutdown line *after* the JSON result line — `asyncio "Event loop is closed"`, a `ResourceWarning`, a multiprocessing "leaked semaphore" line, or a grpc/aiohttp atexit message. `JSON.parse(stdout)` then throws, the branch returns `{ ok:false, status:502, error:"Pipeline returned non-JSON output" }`, and the entire (already-paid-for) analysis is reported to the recruiter as a failure.
- **Root cause**: This is exactly the failure mode `parsePythonJson` was written to defend against — and reasoning-run.ts:52-56 documents that it deliberately uses `parsePythonJson` "because reasoning_cli invokes an LLM, and the interpreter can print shutdown chatter after the JSON line." `analyze-run` is the *same* class of LLM-invoking CLI but still uses `JSON.parse(stdout)` directly, leaving it unprotected. (It also passes only `stdout` to the schema path, so the error message lacks the stderr context `parsePythonJson` embeds.)
- **Impact**: Intermittent, environment-dependent 502s on successful analyses — the most visible, most expensive user action in the app — with the result silently discarded and the cache never populated, so the retry pays again. Hard to reproduce on a clean machine, painful in CI/prod where shutdown ordering differs.
- **Fix sketch**: Replace `JSON.parse(stdout)` with `parsePythonJson<unknown>(stdout, stderr)` (already imported pattern in sibling runners), wrapped in the existing try/catch so a genuine non-JSON run still degrades to the 502 branch with stdout+stderr in the message.

## 3. `dedupe_key` has no UNIQUE constraint — duplicate concurrent runs across processes/connections
- **Severity**: Medium
- **Category**: race-condition
- **File**: app/_lib/db.ts:271 (`idx_tasks_dedupe` is a plain, non-unique index) + tasks.ts:182-189 (check-then-insert)
- **Scenario**: `startTask` does a read (`getActiveTaskByDedupe`) then a write (`createTask`) with no atomicity at the storage layer. Within one Node process the two synchronous better-sqlite3 calls can't interleave, so the in-process case is safe. But the codebase explicitly runs *multiple writers on the same kp.sqlite* (db.ts:128-131 notes the scheduler writes on its own connection; instrumentation.ts ticks the scheduler which can spawn policy/automation work; an external cron can hit `/api/automation/run`). Two writers that both decide to start, e.g., the singleton `batch_screen` or a `group_eval` for the same role can both pass the active-by-dedupe check and both INSERT, since nothing at the DB level forbids two `('queued'|'running')` rows with the same `dedupe_key`.
- **Root cause**: Dedup is enforced only by an application-level read-then-write, and the supporting index `(dedupe_key, status)` is intentionally non-unique. The "one run per role / one batch-screen at a time" invariants encoded in task-dedupe.ts are therefore advisory, not guaranteed.
- **Impact**: Duplicate concurrent LLM runs for the same identity — double cost, double side effects (e.g. two `batch_screen` passes both advancing the same pipeline entries), and a confusing double row in the tasks view. Rare today because most spawns funnel through one process, but the multi-connection architecture makes it reachable, and it's exactly the class of bug the dedupe machinery claims to prevent.
- **Fix sketch**: Add a partial UNIQUE index on active rows — `CREATE UNIQUE INDEX … ON tasks (dedupe_key) WHERE status IN ('queued','running')` (guard the creation like the dev_submissions dedup index at db.ts:433-440 in case legacy duplicates exist). Catch the UNIQUE violation in `createTask`/`startTask` and fall back to returning the existing active row, making dedup atomic instead of best-effort.

## 4. `setTaskProgress` / `markTaskRunning` can resurrect or mutate a terminal task (no status guard)
- **Severity**: Medium
- **Category**: state-corruption
- **File**: app/_lib/db.ts:2221-2229 (`markTaskRunning`, `setTaskProgress`); interplay with finishTask:2250 and cancelTask in tasks.ts:195-208
- **Scenario**: A task is canceled (`cancelTask` → `controller.abort()`), and `runOne` records it `finished` as "canceled". The handler, however, keeps running (see finding #1, or simply an in-flight `ctx.progress(...)` callback that resolves a tick later) and calls `progress(done,total,msg)` → `setTaskProgress`, which does `UPDATE tasks SET progress_done=…, progress_msg=… WHERE id=?` with **no status predicate**. A late straggler write lands on the already-terminal row. Worse, on a restart `interruptStaleTasks` marks a 'running' orphan 'interrupted'; if a leaked handler from the previous process were still alive (it isn't, after restart) the same unguarded UPDATE pattern would clobber it — and within one process, a recovery-re-enqueued task whose previous controller is gone can still receive a `markTaskRunning` that overwrites `started_at`.
- **Root cause**: The task lifecycle mutators write unconditionally by `id` and never assert the row is still in a non-terminal state, so the "terminal is final" invariant is enforced only by in-memory bookkeeping (`controllers`, `running`) that does not survive a restart and does not bind the late progress callback.
- **Impact**: A canceled/interrupted task can show stale progress text ("Screening Jana K…") after it's dead, and `started_at`/progress can be silently overwritten — confusing operators reading the Background-tasks view and the readiness probe. Not data-destroying, but it erodes trust in the task status surface the whole feature is built on.
- **Fix sketch**: Add `AND status IN ('queued','running')` (or `AND status NOT IN (<terminal set>)`) to the `markTaskRunning` and `setTaskProgress` UPDATEs so writes to a terminal row are no-ops. `finishTask` could likewise guard to make the first terminal transition win.

## 5. `codegen.py --check` crashes on a non-UTF-8/locked generated file instead of reporting "out of date"
- **Severity**: Low
- **Category**: edge-case
- **File**: pipeline/jobfit/codegen.py:166-178 (`--check` branch) and 155-161 (`write`)
- **Scenario**: `npm run schemas:check` runs `codegen.py --check`, which does `path.read_text(encoding="utf-8")` for each generated file. If `schemas.generated.ts` / `taxonomy.generated.ts` is somehow non-UTF-8 (a bad merge, an editor that rewrote it cp1250 on Windows — the very locale the runner forces `PYTHONUTF8` to dodge), `read_text` raises `UnicodeDecodeError`, which is unhandled and exits the process with a traceback (exit 1, but as a crash, not the intended "out of date" message). Symmetrically, `write()` does `read`-free overwrite so it's fine, but `--check` is the CI gate.
- **Root cause**: The staleness comparison assumes the on-disk file is always readable UTF-8; it conflates "unreadable/corrupt" with neither the clean (exit 0) nor the actionable stale (exit 1 with a clear "run codegen" message) path.
- **Impact**: A corrupt generated file fails CI with an opaque `UnicodeDecodeError` traceback instead of the helpful "X out of date. Run `python -m pipeline.jobfit.codegen`." message — minor developer-experience papercut, and only on an already-broken file.
- **Fix sketch**: Treat any read failure (missing handled already, plus `UnicodeDecodeError`/`OSError`) as "stale": wrap the per-file read in try/except and append the path to `stale` on failure, so `--check` always degrades to the actionable message rather than a crash.

## 6. Opportunistic prompt-cache prune scans the whole table on a random 2% of writes with no index on the comparison form
- **Severity**: Low
- **Category**: edge-case
- **File**: app/_lib/db.ts:789-803 (`prunePromptCache` via `storePromptCache`)
- **Scenario**: `prunePromptCache` runs `DELETE FROM gemini_cache WHERE expires_at < ?` where `?` is `new Date().toISOString()`. There IS an index `idx_gemini_cache_expires ON (expires_at)` (db.ts:171), so the range delete can use it — good. But the boot prune (db.ts:455-460) and the 2%-of-writes opportunistic prune both fire `DELETE`s inside the same single WAL connection that serves live reads; on a large, mostly-expired cache the delete is a long write that holds the write lock while every analyze/reasoning request's `storePromptCache` (and the scheduler's separate connection) contends, and `busy_timeout=5000` makes those wait up to 5s. The 2% trigger means it strikes unpredictably on a user-facing write path rather than off-peak.
- **Root cause**: GC is amortized onto the hot write path with no bound on how much it deletes per pass; a long-idle deployment that boots with a huge expired backlog, or a sudden flood of expiries, turns one unlucky `storePromptCache` into a multi-second stall that can ripple into SQLITE_BUSY on the other connection.
- **Impact**: Occasional latency spikes / busy contention on the analyze/reasoning write path proportional to expired-row backlog. Low severity because the expiry index keeps the common case fast and prunes are infrequent, but the unbounded per-pass delete on the hot path is a latent foot-gun.
- **Fix sketch**: Bound each opportunistic pass (`DELETE … WHERE expires_at < ? LIMIT N` via a subselect on rowid, or a count-gated skip), and/or move pruning off the request write path (the boot prune already exists; a periodic scheduler-driven prune would remove it from `storePromptCache` entirely).
