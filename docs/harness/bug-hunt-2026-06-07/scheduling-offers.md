## 1. Reminder sweep ignores pipeline-entry status — reminds rejected/declined/hired candidates
- **Severity**: High
- **Category**: recovery-gap
- **File**: C:/Users/mkdol/dolla/kp/app/_lib/schedule-store.ts:205 (dueReminders), C:/Users/mkdol/dolla/kp/app/_lib/interview-reminders.ts:29
- **Scenario**: Candidate confirms a slot (invite -> `confirmed`, `slot_at` set). Hours later the recruiter rejects them, the candidate declines the offer, or they get Hired and the interview is moot. The slot is still > now and < now+24h, so the next heartbeat sweep picks the invite up and emails the candidate "reminder: your interview is at <slot>". Nothing ever clears the confirmed invite when the linked entry leaves the interview track.
- **Root cause**: `dueReminders` selects purely on `schedule_invites` columns (`status='confirmed' AND slot_at IS NOT NULL AND reminder_sent_at IS NULL AND reminder_attempts < ?`). It never joins `pipeline_entries` to check the entry is still active/interview-stage, and no rejection/decline path cancels or marks the invite. (The repo's own idea-d7a8d30e "stop reminding candidates of cancelled..." documents this exact divergence and is still unresolved — only a command file, no code fix.)
- **Impact**: A rejected or withdrawn candidate receives a confidence-building "see you at your interview" email for a call that will never happen. Direct, candidate-facing, trust-eroding message; the invite/pipeline states silently diverge with no operator signal (unlike the `needs_reconcile` path, which only covers the inverse failure).
- **Fix sketch**: In `dueReminders`, join the entry and exclude invites whose entry `status NOT IN ('active', …)` or whose stage has passed Interview — e.g. `JOIN pipeline_entries p ON p.id = entry_id WHERE p.status = 'active'`. Or add a `cancelScheduleInvite(entryId)` write invoked from the `reject`/`decline` transitions that flips `status` to a terminal `cancelled` so the partial due-index drops it. Prefer the cancel-on-transition approach so the index stays a pure range scan.

## 2. A still-valid scheduling token lets a candidate book an interview for an already-rejected/declined entry
- **Severity**: High
- **Category**: edge-case
- **File**: C:/Users/mkdol/dolla/kp/app/api/schedule/[token]/route.ts:55 (GET 37), C:/Users/mkdol/dolla/kp/app/_lib/db.ts:3027 (approve_event)
- **Scenario**: Recruiter mints a schedule link, then rejects the candidate before they open it (or the candidate is declined elsewhere). The candidate opens `/schedule/<token>`: GET returns the invite + a fresh slot list (no entry-status check), they pick a slot, POST confirms it, and `actOnPipelineEntry(entry.id, "approve_event", slot)` runs. `actOnPipelineEntry` does NOT guard on `row.status` (db.ts:3007-3026 only checks existence and optional `expectedStage`), so it re-sets `approval_kind='calendar'`/moves stage to Interview while `status` stays `rejected`, and writes a `scheduled` activity event for a dead candidate. The candidate sees "You're booked" and gets a confirmation email.
- **Root cause**: Neither the token GET/POST nor `approve_event` validate that the linked pipeline entry is still in a bookable state. The token is treated as proof of a still-valid interview slot — an assumption the prompt explicitly calls out ("a token maps to a still-valid entry").
- **Impact**: A rejected candidate is told they're booked and emailed a confirmation; the recruiter board shows a `scheduled` event and a reactivated approval on a terminal entry — a confusing, embarrassing divergence that also feeds finding #1's reminder.
- **Fix sketch**: In the confirm POST (and ideally GET, to short-circuit the picker), load the entry and reject if `entry.status !== 'active'` (return 410/409 "This interview is no longer available"). Defense-in-depth: have `approve_event` in `actOnPipelineEntry` no-op + return null when `row.status` is terminal (`rejected`/`declined`/`hired`), mirroring the `expectedStage` skip.

## 3. Recruiter calendar picks ("Tue 14:00") never match the candidate token slot format — schedule-tab confirms persist a placeholder slot
- **Severity**: Medium
- **Category**: state-corruption
- **File**: C:/Users/mkdol/dolla/kp/app/features/sub_schedule/ScheduleTypes.ts:18-19, C:/Users/mkdol/dolla/kp/app/features/sub_schedule/ScheduleTab.tsx:150, C:/Users/mkdol/dolla/kp/app/_lib/schedule-slots.ts:28
- **Scenario**: In the recruiter Schedule tab, picks are display strings like `"Tue 14:00"` (`DEFAULT_SLOT`, calendar grid labels `${d} ${t}`). Confirming sends `detail: picks[e.id]` to `approve_event`, which stores `"Tue 14:00"` verbatim as the slot and emits it on the `scheduled` event. But the candidate-facing canonical slot label is `"Tue 14 Jun · 14:00"` with a real ISO `slot_at` (schedule-slots.ts `slotLabel`). The recruiter-side "Tue 14:00" has no date and no `slot_at`, so it can never line up with `bookedSlots()`/collision identity or generate a timed reminder.
- **Root cause**: Two parallel slot vocabularies. The token flow was hardened to mint server-authored labels + ISO `slot_at`; the recruiter calendar tab still uses the legacy weekday+time placeholder with no date/ISO, and `approve_event` trusts the raw `detail`.
- **Impact**: Interviews "scheduled" from the recruiter calendar carry a dateless, year-ambiguous slot ("Tue 14:00" — which Tuesday?), produce no `slot_at`, get no timed reminder, and are invisible to double-booking collision detection. A candidate confirming a real dated slot via their token and a recruiter "moving" them on the calendar can silently disagree on the actual time.
- **Fix sketch**: Make the recruiter calendar speak the same vocabulary: derive concrete dated slots (label + ISO `value`) the same way `proposeSlots` does, and route recruiter confirms through the same validated `slot`/`slot_at` write so collision + reminder logic applies uniformly. At minimum, stamp a real date on the picked slot before persisting.

## 4. `offeredSlotFor` uses server-local wall-clock for business-day/time checks — DST and timezone-edge slots are silently rejected or shifted
- **Severity**: Medium
- **Category**: timezone
- **File**: C:/Users/mkdol/dolla/kp/app/_lib/schedule-slots.ts:62-75 (also proposeSlots 36-56)
- **Scenario**: `proposeSlots` builds slot ISO values from `new Date()` + `setHours(10|14, ...)` in the server's local zone, then `.toISOString()`. `offeredSlotFor` re-parses the submitted ISO and validates with `slot.getDay()`/`getHours()`/`getMinutes()` — again server-local. (a) Across a DST transition between proposal and confirm, the same wall-clock "14:00" maps to a different UTC instant, so a slot proposed before the change can fail the exact-minute check after it (`getMinutes() === m` still holds, but on the spring-forward day a 14:00-local value that crossed the boundary can land on a non-existent/duplicated local hour and shift). (b) On a server set to UTC while candidates are elsewhere, "business hours / weekend" are evaluated in the wrong zone, so a slot that is Saturday or 3am for the candidate is treated as valid (or a legitimate Friday-evening slot for the candidate is rejected as weekend).
- **Root cause**: Slot identity, business-day rules, and the candidate's experienced time are all collapsed onto whatever zone the Node process happens to run in. No explicit interview timezone is pinned.
- **Impact**: On DST days and non-local deployments, valid candidate picks get "That time isn't one of the offered slots" (silent dead-end on a public page), or out-of-hours/weekend times slip through. The displayed label can also disagree with the candidate's local clock. Low-frequency but real, and exactly the latent timezone/DST class flagged for this context.
- **Fix sketch**: Pin an explicit interview timezone (e.g. `Europe/Prague`) and do day/hour/minute validation against that zone (Intl.DateTimeFormat with `timeZone`, or a small tz helper) rather than the process-local `getDay`/`getHours`. Keep `slot_at` as the UTC instant but derive both proposal and validation from the same pinned zone so they cannot drift across a DST boundary.

## 5. Confirm route swallows confirmation-email failure as success ("We've sent a confirmation") on the candidate page
- **Severity**: Medium
- **Category**: silent-failure
- **File**: C:/Users/mkdol/dolla/kp/app/api/schedule/[token]/route.ts:97-108, C:/Users/mkdol/dolla/kp/app/schedule/[token]/SchedulePicker.tsx:93-95
- **Scenario**: Candidate confirms a slot. The slot is recorded and the route returns `{ ok: true }`. The confirmation dispatch (`dispatchInterviewConfirmation`) is wrapped in `try { … } catch { /* best-effort delivery */ }`. If delivery throws (comms provider down, bad address), the candidate still sees the success card stating "We've sent a confirmation and will remind you before the call." For a **short-notice** booking (< 2h out), `dueReminders` deliberately suppresses the timed reminder because the confirmation "IS the reminder" — so if that confirmation silently fails, the candidate gets *zero* notifications for an imminent interview.
- **Root cause**: Confirmation dispatch failure is swallowed with no persisted signal and no effect on the response, and the success copy unconditionally promises a confirmation was sent. Unlike the reminder path (bounded retry + loud log) and the reconcile path (`needs_reconcile` flag), a failed confirmation leaves no trace.
- **Impact**: Candidate believes they're confirmed and will be reminded; for short-notice bookings they may receive no communication at all and miss the interview. Recruiter has no visibility.
- **Fix sketch**: Don't claim delivery unconditionally — capture the dispatch result and either retry via the same heartbeat machinery or flag the invite (reuse a `needs_reconcile`-style column / log to `logScheduleReconcile`) when it throws. For short-notice bookings especially, surface a softer "we'll be in touch to confirm" message if delivery could not be verified.

## 6. Offer page leaves stale `result` after a failed POST when the offer was responded elsewhere; "already responded" treated as accepted on a missing row
- **Severity**: Low
- **Category**: edge-case
- **File**: C:/Users/mkdol/dolla/kp/app/_lib/offer-finalize.ts:37-39,52-54; C:/Users/mkdol/dolla/kp/app/offer/[token]/page.tsx:52
- **Scenario**: In `respondToOffer`, when the CAS loses (`!claimed`), the code derives the reported status as `claimedOffer?.status === "accepted" ? "accepted" : "declined"`. If `markOfferResponded` returns `offer: null` (row vanished, or the token row could not be re-read), the optional-chain yields `undefined`, so the branch falls to **"declined"** — telling a candidate whose accept lost the race that their offer was *declined*. The inverse on the page: a GET that loads `status: 'extended'` then a POST that fails network-side leaves the buttons re-enabled (good), but a concurrent accept-by-recruiter between GET and the candidate's POST returns `alreadyResponded` with the recruiter's status, which can flip an "Accept" click into a "declined" confirmation screen.
- **Root cause**: The loser-branch status inference defaults ambiguous/null outcomes to `"declined"` rather than re-reading the authoritative row, and there is no "could not determine" state.
- **Impact**: Rare, but a candidate could be shown the wrong terminal outcome (told they declined when they accepted) on a double-submit / concurrent-response edge. Misleading on an irreversible, high-stakes screen.
- **Fix sketch**: In the `!claimed` branch, re-fetch the authoritative offer (`getOfferByToken`) and report its actual `status`; if it is still `extended` or unreadable, return an error/"please refresh" rather than defaulting to `declined`. On the page, treat an unexpected status mismatch as a reload prompt instead of rendering a terminal screen.
