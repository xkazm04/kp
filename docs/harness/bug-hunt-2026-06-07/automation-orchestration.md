## 1. Cached outreach re-sends a real candidate email on every invocation
- **Severity**: Critical
- **Category**: idempotency
- **File**: C:/Users/mkdol/dolla/kp/app/_lib/automation-run.ts:189-193 (with C:/Users/mkdol/dolla/kp/app/_lib/automation-run.ts:105-138 and C:/Users/mkdol/dolla/kp/app/_lib/comms.ts:36-41)
- **Scenario**: A recruiter runs the `outreach` task for an entry (button → `/api/automation/outreach`, or the background `automation` task). The result is computed and `storePromptCache` writes it under `cacheKey` for `TTL_HOURS=168`. Anytime in the next 7 days the same `outreach` is triggered again — a double-click, a refresh-driven retry, a re-run after the operator wasn't sure it "took", or the same entry re-screened then outreach'd again with the same profile/job/notes — `lookupPromptCache` returns the cached payload, the Python hop is skipped, BUT the apply block at line 189-193 still executes `await dispatchOutreach(entry, result)` unconditionally. `dispatchOutreach` → `sendComm` → `recordOutbox` inserts a brand-new outbox row (`recordOutbox` has no dedup, db.ts:2588) and, with `COMMS_WEBHOOK_URL` set, the `WebhookChannel` actually POSTs the message to the relay (comms.ts:51-55). The cache makes the *computation* idempotent but the *side effect* is re-fired every time.
- **Root cause**: The prompt cache was designed to make regeneration cheap/stable, but the side-effecting dispatch (`dispatchOutreach`) sits AFTER the cache boundary and is not guarded by any "already sent for this entry/version" check. A cache HIT is treated as "recompute for free" when for `outreach` it should mean "already delivered — do not resend."
- **Impact**: Duplicate first-contact emails to candidates (spam, looks unprofessional in a hiring tool), inflated `outreach_sent` audit events, and with a live relay, repeated external sends — exactly the "retry storm / double-execution" class. The cache TTL (168h) widens the collision window to a full week.
- **Fix sketch**: Gate the dispatch on a per-entry idempotency record rather than the prompt cache. Before `dispatchOutreach`, check `hasEventToday(entry.id, "outreach_sent")` (or an unbounded "ever sent for this version" lookup) and skip the send if already delivered; only the draft should be served from cache. Alternatively, decouple: cache the draft, but make the *send* conditional on the absence of a prior `outreach_sent`/outbox row keyed by `(entryId, version)`.

## 2. Manual / single-task `screen` applies its stage move without the expectedStage CAS
- **Severity**: High
- **Category**: race-condition
- **File**: C:/Users/mkdol/dolla/kp/app/_lib/automation-run.ts:158 (and the `accept` in the screen branch generally, 154-163)
- **Scenario**: `runAutomationTask` reads `entry` (and `entry.stage`) at line 73, then spends seconds in the Python `screen` hop (or, on a cache miss, the LLM CLI which can take up to its 120s timeout). When it returns, the screen branch calls `actOnPipelineEntry(entry.id, "accept")` at line 158 with NO `expectedStage` option. During that window a recruiter (Decisions queue), a concurrent policy pass, or another `/[task]` call may have already advanced/rejected the entry. Unlike the policy pass — which was hardened to pass `expectedStage: snapshotStage` to make stale verdicts a no-op (automation-pass.ts:85-101) — this manual/background single-task path applies the move blind to whatever stage the entry is in NOW.
- **Root cause**: The CAS hardening (idea-b6310b92) was applied only to the batch policy pass. The single-task path (used by `/api/automation/[task]` and the background `automation`/`batch_screen` runners) was left calling `actOnPipelineEntry` without an `expectedStage` guard, even though it has the same read→Python-hop→apply gap.
- **Impact**: A screen decided against an Accepted entry can be applied after the entry already reached Interview/Offer, advancing it an extra stage (e.g. Interview→Offer) or re-opening/moving a rejected entry. `batchScreen` (tasks.ts:59-77) loops this across every Screened entry, amplifying the window. Candidate progressed past the human gate on a stale verdict.
- **Fix sketch**: Thread the snapshot stage through: capture `const snapshotStage = entry.stage` before the Python hop and call `actOnPipelineEntry(entry.id, "accept", undefined, { expectedStage: snapshotStage })`; when it returns `null`, downgrade `applied` to a "skipped: stage changed" result instead of also running `setApproval`. Note the Accepted-stage double-action (advance + holdForReview) must re-read or re-check stage so the `setApproval`/event at 159-161 doesn't land on a now-unexpected stage.

## 3. Forced manual tick after enabling the schedule double-fires within ~60s
- **Severity**: High
- **Category**: race-condition
- **File**: C:/Users/mkdol/dolla/kp/app/api/automation/schedule/route.ts:16-18 (with C:/Users/mkdol/dolla/kp/app/_lib/scheduler.ts:15 and C:/Users/mkdol/dolla/kp/app/_lib/scheduler-store.ts:98-110)
- **Scenario**: A user POSTs `/api/automation/schedule` with `{ enabled: true, tick: true }` (the natural "turn it on and run it now" action). `setEnabled(POLICY_JOB, true)` sets `next_due_at = now` (scheduler-store.ts:103-108). Then `tickScheduler({ force: true })` runs at line 18; because `force` is true it SKIPS `claimDueRun()` (scheduler.ts:15) — so it runs the pass but never advances `next_due_at`. `next_due_at` is left at `now` (already due). The instrumentation heartbeat (every 60s) then calls `tickScheduler()` (no force), `claimDueRun()` sees `next_due_at <= now`, wins the claim, and runs the pass a SECOND time.
- **Root cause**: A forced tick deliberately bypasses the clock claim, but it does not reconcile the schedule's `next_due_at`/`last_run_at` afterward. `recordRun` updates only `last_summary_json` (scheduler-store.ts:182-188), not `last_run_at`/`next_due_at`. So a force-run leaves the clock still pointing at an overdue window the next heartbeat happily claims.
- **Impact**: Two full policy passes within a minute. The in-process single-flight (`inFlightPass`) only collapses passes that OVERLAP in time; the forced pass typically finishes well before the next 60s heartbeat, so the second pass is a genuine separate execution over a fresh snapshot — re-evaluating aging alerts, re-attempting moves, and (combined with finding #5) potentially re-sending rejection comms for entries that aged into a new decision. Also pollutes the run log with a spurious extra run.
- **Fix sketch**: After a successful forced tick, advance the clock (e.g. call `claimDueRun()`-style `next_due_at = now + interval` reconciliation, or have `tickScheduler({force})` stamp `last_run_at`/`next_due_at` via a store helper). Simplest: when `force` and the job is enabled, set `next_due_at` to `now + intervalMinutes` after the pass records OK, so the next heartbeat doesn't immediately re-claim.

## 4. A comms throw mid-loop aborts the policy pass, leaving applied rejects orphaned and remaining entries unprocessed
- **Severity**: High
- **Category**: recovery-gap
- **File**: C:/Users/mkdol/dolla/kp/app/_lib/automation-pass.ts:78-130 (specifically the unguarded `await dispatchRejection` at 103)
- **Scenario**: The policy pass iterates `decisions`. For a reject it first commits the DB transition (`actOnPipelineEntry(..., "reject")` at line 101, which atomically sets status='rejected' and logs the event), THEN `await dispatchRejection(rejected, { automated: true })` at line 103. `dispatchRejection` → `sendComm`. With `COMMS_WEBHOOK_URL` configured, a non-2xx/non-retryable response path still resolves, but a thrown error is possible (e.g. `recordOutbox` SQLITE_BUSY beyond the 5s busy_timeout under heavy contention, or an unexpected fault in the channel). Any throw inside the loop is NOT caught per-iteration — it propagates out of `executeAutomationPass`, rejecting the whole pass.
- **Root cause**: The apply loop has no per-decision try/catch. One task's failure aborts the aggregate pass. Worse, the failing entry's DB reject was already committed at line 101 before the comm threw, so state and notification diverge, and every decision AFTER the failing one in the array is silently skipped this pass.
- **Impact**: Partial-failure with orphaned state: a candidate is marked rejected in the DB but never receives the rejection email, and the pass reports `error` (tickScheduler records status="error") discarding the summary of everything already applied. Subsequent due entries (advances, holds, alerts) are skipped until the next tick. A single transient comms hiccup turns a clean board-wide pass into a half-applied one — the "a task throws but earlier writes persist / later tasks never run" class.
- **Fix sketch**: Wrap each decision's apply+dispatch in a try/catch that records the per-entry error (into `d` and/or an `errors` counter on the summary) and continues to the next decision, so one failure can't abort the batch. For the reject path specifically, make the order recoverable: either send-then-commit, or treat a post-commit comm failure as a queued retry (dead-letter) rather than a thrown pass abort — mirroring the bounded-retry model already used by `sendDueInterviewReminders`.

## 5. Re-running `rematch` re-emits a `rematched` event (and re-fires its alert/audit) even though the entry create is idempotent
- **Severity**: Medium
- **Category**: idempotency
- **File**: C:/Users/mkdol/dolla/kp/app/_lib/automation-run.ts:172-188
- **Scenario**: `rematch` on a cache MISS scores the live corpus and, when a match is found, calls `createPipelineEntry` (idempotent — keyed `m-{candidateId}-{jobId}`, db.ts:1814-1832) then `recordAutomationEvent(entry.id, "rematched", ...)` at line 184. Because rematch's cache key is bound to the corpus fingerprint, adding/removing ANY job in the corpus self-invalidates the cache (by design, idea-e01935e9), so the next rematch is a fresh MISS that re-runs the whole apply block. `createPipelineEntry` returns the existing entry (good), but `recordAutomationEvent` unconditionally appends another `rematched` event every time, and `applied` reports `"rematched"` as if a new placement happened.
- **Root cause**: The idempotency guard lives inside `createPipelineEntry` (it returns `{created:false}` for an existing entry) but the caller ignores the `created` flag and logs the event regardless. The audit/event side effect is not gated on whether a new entry was actually created.
- **Impact**: Duplicate `rematched` audit events inflate the activity feed and any metrics counting rematches; an operator re-running rematch (or a corpus edit re-triggering it) sees repeated "rematched to X" entries for a single real placement. Lower severity than #1 because no external/candidate-facing message is sent and the entry itself isn't duplicated.
- **Fix sketch**: Use the returned `created` flag: `const { created } = createPipelineEntry({...})`; only `recordAutomationEvent(..., "rematched", ...)` and set `applied = "rematched"` when `created` is true, else report `applied = "already_rematched"` (or "no_change").

## 6. Alert dedup window uses UTC midnight, diverging from the operator's local "today"
- **Severity**: Medium
- **Category**: edge-case
- **File**: C:/Users/mkdol/dolla/kp/app/_lib/db.ts:1995-2002 (hasEventToday), used by C:/Users/mkdol/dolla/kp/app/_lib/automation-pass.ts:124-129
- **Scenario**: Per-day alert dedup (`aging_alert`, `stale_alert`, `fairness_gate_blocked_reject`) relies on `hasEventToday`, which computes the day boundary with `start.setUTCHours(0,0,0,0)`. The deployment market is the Czech tech market (CET/CEST, UTC+1/+2). For passes that run in the local evening (after 22:00/23:00 local, which is already past UTC midnight), an alert logged at 23:30 local on Monday and again at 00:30 local on Tuesday both fall on the SAME UTC day boundary at some hours, but an alert logged at, say, 01:30 local Tuesday vs 23:00 local Monday straddle the UTC boundary mid-evening — so "once per day" dedup resets at 01:00–02:00 local rather than at local midnight.
- **Root cause**: Day-bucketing math is done in UTC while the operational notion of "today" (and the `daysInStage` aging thresholds that drive these alerts) is implicitly local. The two clocks are misaligned by the CET/CEST offset.
- **Impact**: Aging/stale/fairness alerts can fire twice for one entry within a single local day (or be suppressed across what the operator considers two different days) depending on what local hour the scheduled pass runs — duplicated noise in the Activity feed and inflated `summary.alerts`. Benign but erodes trust in the dedup guarantee, and the effect is timezone/clock-dependent so it surfaces inconsistently.
- **Fix sketch**: Compute the day boundary in the configured business timezone (or document and standardize on UTC everywhere, including the aging thresholds). Either derive `start` from a local-midnight calculation for the deployment TZ, or key dedup on a local-date string (`YYYY-MM-DD` in the business TZ) rather than a UTC timestamp comparison.
