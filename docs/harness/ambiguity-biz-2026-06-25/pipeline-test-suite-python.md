# Pipeline Test Suite (Python) — Ambiguity 🌀 + Business 🚀 scan
> Total: 5 | Lens: 🌀3 / 🚀2 | Severity: C0/H2/M3/L0

Context: a 65-file pytest/unittest suite of unusually high quality — most numeric
pins carry an inline rationale, fairness probes are deliberate, and several
"green theater" traps have already been closed (entry_precision default-to-1.0,
salary coverage-vs-accuracy split, pedigree delta==0). The findings below are
therefore not "the suite is weak" but five specific, high-leverage gaps where a
business-critical or hiring-decision path is under-guarded relative to the bar
the rest of the suite sets.

## 1. Only 1 of ~8 cross-language prompt-version couplings is sync-guarded — scorecard/offer/screen can serve 7-day-stale AI output
- **Lens**: 🌀 Ambiguity
- **Severity**: High
- **Category**: coverage-gap / cross-language-contract
- **File**: pipeline/jobfit/tests/test_prompt_version_sync.py:14
- **Observation**: `test_prompt_version_sync.py` enforces that exactly ONE constant — `REASONING_PROMPT_VERSION` — stays equal to its Node twin in `app/_lib/reasoning-run.ts`, and its docstring frames this as the "codegen --check pattern" to stop a stale cache shipping. But `pipeline/jobfit/automation.py:26-32` defines seven MORE prompt versions (`SCREENING_/OUTREACH_/REJECTION_/PREP_/SCORECARD_/REMATCH_/OFFER_PROMPT_VERSION`) whose values are hardcoded a SECOND time on the Node side in `app/_lib/automation-run.ts:32-40` (`AUTOMATION_VERSION`). That map is the cache-bust axis: `lookupPromptCache(cacheKey, version)` returns null on version mismatch (`app/_lib/db/analyses.ts:247`), so the version string IS the invalidation mechanism. None of these seven (nor campaign/group_compare/devcase versions) has a sync test. The same coupling exists for `normalize_band` ("Mirror of salary-band.ts", finding #4) — parity asserted in prose, enforced for none of them but reasoning.
- **Why it matters**: If someone improves the Python `scorecard` or `offer` prompt and bumps `SCORECARD_PROMPT_VERSION` to retire old outputs, but doesn't also edit the hardcoded `"scorecard-v3"` in `automation-run.ts`, the Node cache keeps serving outputs generated by the OLD prompt for the full 168h TTL — silently, on the interview-scorecard (hiring decision) and offer-letter (monetized/legal) artifacts. This is the exact failure the reasoning test was written to prevent, left unguarded on higher-stakes tasks.
- **Recommendation**: Generalize the existing test: read `AUTOMATION_VERSION` out of `automation-run.ts` and assert each entry equals the corresponding Python constant (one parametrized case per task). Same pattern catches campaign/group_compare/devcase if those versions are also mirrored Node-side.
- **Effort**: S

## 2. The fairness gate has no name / gender / age neutrality probe — and the candidate's name IS carried into the match candidate
- **Lens**: 🚀 Business
- **Severity**: High
- **Category**: coverage-gap / fairness-invariant
- **File**: pipeline/jobfit/eval/matching_eval.py:293
- **Observation**: `run()` ships exactly four fairness probes — pedigree, socioeconomic, language, monotonicity (`matching_eval.py:293-298`). `_probe_pedigree` (`:186-216`) is a strong template: it asserts a sentinel university token is absent from `repr(build_match_candidate(...))` AND that the top-score delta is exactly 0. There is NO equivalent probe for the candidate's NAME — yet `build_match_candidate` explicitly RETAINS `display_name` as `label` (`pipeline/jobfit/transform.py:191`: `label=profile.display_name or "Candidate"`), so unlike `education_detail` the name is not dropped. The blind-redaction module treats name/gender pronouns/age as the protected set (`redact.py` header), confirming the product's own threat model — but the deterministic matching gate never asserts that name/gender/age can't move the score.
- **Why it matters**: For an EU-AI-Act Annex-III high-risk recruitment system, "the applicant's name cannot influence the score" is the single most legally sensitive fairness invariant, and it is the one the gate doesn't test. A future refactor that folds `label` into any text-overlap feature (or a Gemini prompt change that conditions on the name) would introduce gender/ethnic-proxy bias with zero failing test. The product markets fairness heavily (`app/features/sub_about/AboutCoverageData.ts:567`, `FairnessPanel.tsx`), so the claim currently outruns the evidence.
- **Recommendation**: Clone `_probe_pedigree` into `_probe_name_neutral` and `_probe_age_neutral`: set distinctive `display_name` / birth-year tokens, assert the score delta is exactly 0 and the token is absent from the scored feature surface (label may carry it for display, but it must not reach any scoring path). Add both to the probe list so they gate CI.
- **Effort**: S

## 3. The fairness + accuracy eval emits a polished, brief-"centrepiece" report that exists only for CI — a publishable trust/compliance asset left dark
- **Lens**: 🚀 Business
- **Severity**: Medium
- **Category**: dark-capability / monetizable-asset
- **File**: pipeline/jobfit/eval/matching_eval.py:334
- **Observation**: `_format_markdown` (`:334-380`) renders a full report — verdict banner, aggregate-metrics table, per-scenario table, and a fairness-probe section deliberately set apart as "the hero of the report" (`:355-374`) — plus a `--json` mode (`:416-429`). A grep for `matching_eval`/`fairness` across `app/**` shows the IN-APP "fairness" surfaces (`FairnessPanel.tsx`, group-eval) are a DIFFERENT artifact (per-shortlist matrix); this deterministic harness report is consumed nowhere in the product. It runs only as a CI gate.
- **Why it matters**: EU-AI-Act high-risk recruitment requires transparency/eval documentation, and trust is a sales differentiator the app already leans on in marketing copy. This harness is ~80% of a customer-facing "Fairness & Accuracy datasheet" (deterministic, no API key, already versioned by corpus). Surfacing it as a gated report endpoint / downloadable PDF turns an internal gate into a compliance artifact and a trust selling point at near-zero incremental build cost.
- **Recommendation**: Wire a token-gated `/api/report/fairness` (or an admin "Trust report" page) that runs `matching_eval.run()` and renders the existing markdown/JSON; snapshot-test the rendered report so the published asset can't silently regress.
- **Effort**: M

## 4. Salary-band normalization claims TS↔Python parity in a comment but no test enforces it — UI band can drift from the pipeline band
- **Lens**: 🌀 Ambiguity
- **Severity**: Medium
- **Category**: undocumented-contract / parity-claim-untested
- **File**: pipeline/jobfit/tests/test_salary_band.py:18
- **Observation**: `test_salary_band.py` pins Python `normalize_band` / `band_error` against fixtures, with comments asserting each is a "Mirror of salary-band.ts `normalizeSalaryBand` / `salaryBandError`" (`:5-7`, `:18`). The Node counterpart genuinely exists (`app/_lib/salary-band.ts:63` `normalizeSalaryBand`). But the test only pins the PYTHON behavior — it never reads or compares the TS implementation, so the "mirror" is enforced by prose, not by code. The rounding step (nearest 5000, `round_salary`) and the swap-vs-reject rules are duplicated in two languages with nothing keeping them equal.
- **Why it matters**: The candidate and recruiter see the TS-normalized band in the UI/JD, while the pipeline scores/winnability-checks the Python-normalized band. If the TS step changes (e.g. 5000→1000, or the reversed-range repair diverges) the two silently disagree, so a salary the candidate was shown is not the salary the engine reasoned about — a quiet data-integrity defect on a comp-sensitive, trust-sensitive surface.
- **Recommendation**: Add a parity test that drives BOTH implementations over a shared fixture table (run the TS `normalizeSalaryBand` via the Node test runner against the same `NORMALIZE_CASES`, or extract the cases to a shared JSON both suites load), so a one-sided change fails CI.
- **Effort**: S

## 5. Real-world PDF extraction + Gemini skill-recall quality is permanently skipped — only a synthetic fixture gates the pipeline's first stage
- **Lens**: 🌀 Ambiguity
- **Severity**: Medium
- **Category**: coverage-gap / skipped-in-ci
- **File**: pipeline/jobfit/tests/test_pdf_parsing_quality.py:31
- **Observation**: Of the four parsing-quality tests, three are `@unittest.skipUnless(...)`-gated and never run in CI: `test_pypdf_extracts_linkedin_export_well` (`:31`, "personal CV fixture removed"), `test_pypdf_collapses_letter_spaced_text_real_cv` (`:49`), and `test_gemini_pdf_extraction_returns_structured_skills` (`:55`, needs fixture + API key). Only the synthetic letter-spacing collapse (`:38`) always runs. These skips are baked into the tolerated `SKIP_BASELINE=4` in `run_gated.py:25`, so they never trip the tripwire. The synthetic fixture proves the collapse FUNCTION works on a hand-crafted input; nothing proves a real LinkedIn export extracts >5000 clean chars, or that Gemini returns ≥5 structured skills from a real CV.
- **Why it matters**: PDF→text→structured-profile is stage 0 of the entire pipeline; garbage extraction silently poisons every downstream score, match, salary, and offer. The quality bar for the real-world path is asserted only by tests that don't run, so a regression in `extract_text` quality or a drop in Gemini skill recall would ship green.
- **Recommendation**: Commit 1-2 synthetic-but-realistic CV PDFs (no personal data) that exercise the >5000-char + zero-letter-spacing assertions so `:31`/`:49` run unconditionally; gate the Gemini-recall test behind a recorded/stubbed response (like the i18n/blind-mode prompt-capture tests already do) so it runs keyless instead of skipping.
- **Effort**: M
