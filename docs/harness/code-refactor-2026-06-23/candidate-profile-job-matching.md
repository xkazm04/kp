## 1. The `"duplicate"` editor mode is unreachable — dead UI branches
- **Severity**: High
- **Category**: dead-code
- **File**: `app/features/sub_profile/ProfileEditor.tsx:21,238,239` (consumer: `app/features/sub_profile/ProfileTab.tsx:80-103`)
- **Scenario**: `EditorMode = "create" | "edit" | "duplicate"` (ProfileEditor.tsx:21), and the component renders `mode === "duplicate" ? t("headingDuplicate") : …` (line 238) plus the `saveLabel` ternary (line 239) for it. But the editor is instantiated in exactly ONE place — `ProfileTab.tsx`'s `<ProfileEditor mode={editor.mode} …>` (line 82) — and `editor.mode` (an `EditorState`) is only ever set to `"create"` (line 103, `onNewProfile`) or `"edit"` (line 64, the deep-link path). I grepped the whole app: `Grep "ProfileEditor|mode: \"duplicate\"" path=app` and `Grep "\"duplicate\"" path=app` — the only `"duplicate"` literals in this context are the type member and the two ternary arms inside ProfileEditor itself; the `sub_library` "duplicate" hit is an unrelated feature. No caller ever passes `mode="duplicate"`, so `headingDuplicate` and the duplicate-path of `saveLabel` are dead, and the `t("headingDuplicate")` i18n key is referenced only by unreachable code.
- **Root cause**: "Duplicate profile" was scaffolded into the editor's mode enum (and ProfileForm's `hydrate()` comments still mention "applied-AI-draft / duplicate"), but the UI affordance that would launch it (a "Duplicate" button on the matrix/list) was never wired — only Create and Edit (deep link) reach the editor.
- **Impact**: Misleads readers into thinking duplication is a live feature; the `"duplicate"` member forces every `mode` switch to handle a case that can't occur; an orphan `headingDuplicate` translation key lingers in the catalogs. Low correctness risk, but a real "is this used?" trap each time someone touches the editor.
- **Fix sketch**: Either (a) wire a real "Duplicate" entry point (a button on `CandidateMatrix`/the editor that calls `setEditor({ mode: "duplicate", editingId: null, initialPayload: <cloned payload> })`) if the feature is wanted, or (b) remove `"duplicate"` from `EditorMode`, collapse the `heading`/`saveLabel` ternaries to the `edit`/`create` binary, and delete the now-unused `headingDuplicate` key from the i18n catalogs. Pick one; today it is half-built.

## 2. The live-corpus hand-off block is copy-pasted across four spawn sites
- **Severity**: Medium
- **Category**: duplication
- **File**: `app/_lib/reasoning-run.ts:52-57`, `app/api/match/route.ts:47-52` (also out-of-context: `app/api/matrix/route.ts:85-96`, `app/_lib/automation-run.ts:160`)
- **Scenario**: The exact "augment the seed corpus with the live DB jobs" sequence — `const corpusJobs = listCorpusJobs(); if (corpusJobs.length > 0) { writeFile(path.join(workdir,"jobs.json"), JSON.stringify(corpusJobs)); args.push("--jobs-json", jobsPath); }` — appears verbatim in `reasoning-run.ts` and `match/route.ts` (both in scope), and again in `matrix/route.ts` and `automation-run.ts`. I confirmed via `Grep "listCorpusJobs\(\)|jobs.json|--jobs-json" path=app`: four independent copies, each with its own near-identical comment paragraph explaining the DB-wins-on-id-collision contract. Note `match-input.ts` already exists as the shared "resolve + write the candidate/profile input + return inputArgs" helper for the *input* side of these same spawns — the corpus side is the symmetric gap.
- **Root cause**: The corpus override was added per-route as each surface (match, reasoning, matrix, rematch) discovered the same "recruiter-ingested job isn't in the seed" bug; the fix was pasted rather than extracted because each call site assembles its own `args` array.
- **Impact**: A change to the corpus contract (e.g. a fingerprint tweak, a cap on corpus size, switching to a temp-file helper) must land in four places or silently diverge; the cache-key already depends on `computeCorpusFingerprint(corpusJobs.map(j=>j.id))` in reasoning, so a drift between what match sends and what reasoning keys on is a latent correctness hazard.
- **Fix sketch**: Add a small helper next to `match-input.ts`, e.g. `async function appendCorpusJobsArg(args: string[], workdir: string): Promise<JobRecord[]>` that does the `listCorpusJobs` → conditional write → `args.push("--jobs-json", …)` and returns the corpus rows (so reasoning-run can still feed them to `computeCorpusFingerprint`). Replace the four blocks. Behavior-preserving; keep one canonical comment in the helper.

## 3. `MatchResponse.candidate.skills?: number` is a dead field never read by any consumer
- **Severity**: Medium
- **Category**: dead-code
- **File**: `app/features/sub_match/MatchTypes.ts:93`
- **Scenario**: The `candidate` sub-object of `MatchResponse` declares `skills?: number`. The only consumer of `result.candidate` is `Results.tsx` (`const { candidate, meta, matches } = result`), which reads `candidate.label`, `.seniority`, `.roleFamily`, `.archetype`, `.potentialScore`, `.learningSignals`, `.transferableSkills`, `.domainDistance`, `.assumptions`, `.weights`, `.weightBounds` — but never `.skills`. I grepped `Grep "candidate\.skills" path=app`: the only hits are `comparison.ts` and `consent.test.ts`, which operate on a DIFFERENT candidate shape (the analysis candidate, where `skills` is a `string[]`), not this MatchResponse candidate. `Grep "\.skills\b" *.tsx` over the match feature shows MatchCard uses `m.skillsScore` (a `MatchResult` field), not `candidate.skills`. So this `number`-typed field has zero readers and even disagrees in type with the other candidate shapes.
- **Root cause**: Leftover from an earlier match response shape (likely a "skills count" chip that was replaced by the evaluated/ranked Chips and the per-match skill pills).
- **Impact**: An untyped-ish dead field on a contract type invites a future dev to "wire it up" against a value the server may not even send, or to confuse it with the analysis candidate's `string[] skills`. Cosmetic but adds noise to a heavily-relied-on contract.
- **Fix sketch**: Delete line 93 (`skills?: number;`) from the `MatchResponse.candidate` block. Optional/typed-only, so removal is a no-op at runtime; `tsc` will confirm nothing reads it. If the server still emits it, the field just stops being typed (harmless) — but verify against the Python `matching.py` candidate block referenced in the surrounding comment.

## 4. `isStudentish` re-hardcodes the archetype list that `archetypeFieldVisibility` already centralizes
- **Severity**: Medium
- **Category**: duplication
- **File**: `app/features/sub_profile/ProfileEditor.tsx:98` (vs `app/features/sub_profile/ProfileForm.ts:14-22`)
- **Scenario**: ProfileForm.ts deliberately makes `archetypeFieldVisibility(choice)` the "SINGLE SOURCE OF TRUTH" for which archetype-conditional fields show (its header comment, ProfileForm.ts:6-11, calls out that render and submission used to drift and were unified). Yet two lines above the `fieldVis` call, ProfileEditor still computes `const isStudentish = choice === "student" || choice === "auto" || choice === "career_switcher";` (line 98) as a separate hardcoded archetype-id list to gate the enrolled/graduation/wants-change/has-prior signals block (line 304). This is the same "which archetypes get which conditional fields" decision living in a second, independent place — exactly the pattern ProfileForm.ts was created to eliminate. It is also brittle against recruiter-created archetypes: the routing segments are registry-driven (ProfileEditor.tsx:91-96, any custom id is selectable), but `isStudentish` only matches the three baseline ids, so a custom early-career archetype shows years/seniority correctly (via the registry-aware `fieldVis`) yet never shows the student signals.
- **Root cause**: The signals block predates the `archetypeFieldVisibility` extraction; when years/seniority visibility was centralized, the student-signals gate was left as an inline literal.
- **Impact**: Adding/renaming an early-career archetype, or changing which archetypes collect enrollment signals, requires editing this inline literal in addition to the documented single source — the precise drift ProfileForm.ts warns against. Maintenance + correctness (custom archetypes) cost.
- **Fix sketch**: Extend `ProfileForm.ts`'s visibility type with a `signals: boolean` (or a small `archetypeSignalsVisible(choice, scoringModel)` predicate that consults `isEarlyCareer`/the registry's `scoringModel`), and replace the inline `isStudentish` with `fieldVis.signals`. Keep it pure and unit-test it alongside the existing `archetypeFieldVisibility` tests. Behavior-preserving for the three baseline ids.
