## 1. `mk_candidate` factory in `_helpers.py` is dead while ~9 test modules hand-roll `MatchCandidate(...)`
- **Severity**: High
- **Category**: dead-code (and the duplication it was meant to prevent)
- **File**: `pipeline/jobfit/tests/_helpers.py:33-44` (the dead def); callers that should use it: `test_matching.py`, `test_automation.py`, `test_embedding_bridge.py`, `test_match_reasoning.py`, `test_recruiter.py`, `test_recruiter_cli.py`, `test_scoring_contract.py`, `test_weight_proposal.py`, `test_winnability.py`
- **Scenario**: `_helpers.py` ships `mk_candidate(**over) -> MatchCandidate` with sensible defaults, explicitly described as the shared candidate factory ("A MatchCandidate with sensible defaults"). `grep -rn "mk_candidate" .` across the whole repo (`C:/Users/kazda/kiro/kp`) returns ONLY its own definition line plus identical copies in `.claude/worktrees/*` — zero callers. Meanwhile `grep -rn "MatchCandidate(" .` shows ~40 inline constructions across 9 test modules, and three of those files even define their OWN local candidate factory instead of importing the shared one: `test_scoring_contract.py:38 def _student(...)`, `test_winnability.py:10 def _cand(...)`, `test_weight_proposal.py:38-48 def _candidates()`. So the helper meant to kill this duplication is itself unused and the duplication thrives beside it.
- **Root cause**: The shared factory was added to `_helpers.py` (alongside `mkjob`, which *did* get adopted by 5 files) but never wired into the candidate-heavy modules; subsequent tests copied the nearest inline `MatchCandidate(...)` they saw rather than importing.
- **Impact**: A "shared helper" that lies — anyone touching `MatchCandidate`'s required fields/defaults must hunt ~40 call sites instead of one factory, and the dead def gives false confidence that candidates are centralized. Pure maintenance tax; no behavior risk.
- **Fix sketch**: Either (a) adopt it — replace the local `_student`/`_cand`/`_candidates` factories and the most boilerplate-y inline `MatchCandidate(...)` builders with `from ._helpers import mk_candidate`, keeping per-test overrides via kwargs (do NOT collapse cases that assert on distinct field combinations); or (b) if the team prefers per-module factories, delete the dead `mk_candidate` and `MIN_LINKEDIN_TEXT_LEN` to stop advertising a contract nothing honors. Option (a) is preferred since `mkjob` already set the precedent.

## 2. Canned-payload LLM provider stub copy-pasted across ~8 test modules
- **Severity**: High
- **Category**: duplication
- **File**: `test_weight_proposal.py:13-27`, `test_campaign.py:47-59`, `test_interview_scenario.py:42-47`, `test_match_reasoning.py:46-51`, `test_devcase_design.py:16-23`, `test_seed_materializer.py:36-46` (plus `complete_json` stubs in `test_devcase_cli.py`, `test_group_compare.py`, `test_jobs.py`, `test_devcase_provenance.py`, `test_automation.py`)
- **Scenario**: `grep -rln "def complete_json" pipeline/jobfit/tests` returns 11 files; `grep -rn "class .*Provider\|class _Fake\|class _Stub"` shows the same tiny class re-implemented under names `_FakeProvider`, `FakeProvider`, `_StubProvider` over and over. The core shape is identical: `__init__(self, payload)` storing a payload, then `complete_json(self, prompt, system=None): return self._payload`. Reading the bodies confirms near-byte-identical implementations (e.g. `test_interview_scenario.py:42` vs `test_devcase_design.py:16` vs `test_match_reasoning.py:46`). Two slight variants add behavior worth centralizing: an exception-raising path (`test_weight_proposal.py:25 _BoomProvider`; `test_seed_materializer.py:44 raise self._payload if Exception`; `test_campaign.py:50 exc=...`) and an `available()`/prompt-capture (`test_campaign.py:53 self.prompt`, `test_seed_materializer.py:40 available()`).
- **Root cause**: No shared LLM test double in `_helpers.py`, so each LLM-backed feature test grew its own stub; the comment "mirrors ClaudeCliProvider" was copied along with the code.
- **Impact**: When the real provider interface changes (e.g. `complete_json` signature, a new `available()` contract, or how errors surface), 8+ stubs must be updated in lockstep — exactly the drift `_helpers.py` exists to prevent. Today the stubs already disagree on whether they expose `available()` / capture the prompt / raise on Exception.
- **Fix sketch**: Add one `FakeProvider` to `_helpers.py` that subsumes the union: `__init__(self, payload=None, *, exc=None)`, records `self.prompt`/`self.calls`, `complete_json` raises `exc` (or a payload that is an `Exception`) else returns `payload`, and an `available()` returning `True`. Migrate each module to `from ._helpers import FakeProvider`. Keep the keyword-only `system` param to match the real signature. Verify each migrated test still drives its `source == "llm"`/`"deterministic"` branches.

## 3. `mkjob` is shadowed in `test_automation.py` — local def re-wraps the imported one under an alias
- **Severity**: Medium
- **Category**: structure (confusing local shadow)
- **File**: `pipeline/jobfit/tests/test_automation.py:8-16`
- **Scenario**: Line 8 imports the shared factory as `from pipeline.jobfit.tests._helpers import mkjob as _mkjob`, then line 11 defines a module-level `def mkjob(**over)` that just injects a default title and delegates to `_mkjob`. So the module now has two names for almost the same thing (`mkjob`, `_mkjob`) and the public-looking `mkjob` actually shadows the shared symbol. By contrast `test_weight_proposal.py` and `test_scoring_contract.py` handle the same "Backend Engineer default" need with a clearly-private `_job()` wrapper — no alias gymnastics. Confirmed via `grep -rn "^def mkjob\|import mkjob as" test_automation.py`.
- **Root cause**: An author wanted a suite-local default posting but reached for the same public name as the import instead of a `_`-prefixed wrapper, forcing the `as _mkjob` alias to avoid a NameError.
- **Impact**: Low-risk but reads as a bug ("why import mkjob then redefine mkjob?"); invites a future editor to "clean up" the import and silently change defaults. Inconsistent with the `_job()` convention used by sibling modules.
- **Fix sketch**: Rename the local wrapper to `_job(**over)` (matching `test_weight_proposal.py`/`test_scoring_contract.py`) and import the shared factory plainly as `mkjob`; update the ~handful of in-file call sites. Behavior-preserving.

## 4. Named-threshold constants in `_helpers.py` are under-adopted (used only by `test_matching.py`)
- **Severity**: Medium
- **Category**: dead-code (partial) / structure
- **File**: `pipeline/jobfit/tests/_helpers.py:13-16`
- **Scenario**: The module exports four "replacing inline magic numbers across the suite" constants. Grep shows three of them (`STRONG_SKILL_SCORE`, `PARTIAL_SKILL_SCORE`, `MIN_CONFIDENCE_SPREAD`) are referenced ONLY by `test_matching.py`, and `MIN_LINKEDIN_TEXT_LEN` (5000) is referenced by NO file — yet the literal `5000` appears inline at `test_pdf_parsing_quality.py:35` (`assertGreater(summary["length"], 5000)`) and `test_devcase_provenance.py:54`, exactly the magic number the constant was meant to name. Commands: `grep -rln "STRONG_SKILL_SCORE\|PARTIAL_SKILL_SCORE\|MIN_CONFIDENCE_SPREAD\|MIN_LINKEDIN_TEXT_LEN" .` and `grep -rn "5000"`.
- **Root cause**: Same adoption gap as finding #1 — the constants were extracted from `test_matching.py` but the rollout "across the suite" never happened; the docstring overstates reach.
- **Impact**: Constants local to one consumer don't need to live in shared `_helpers.py` (mild structure smell), and `MIN_LINKEDIN_TEXT_LEN` is outright dead while its magic value is duplicated inline in the PDF test that should use it. Misleading docstring.
- **Fix sketch**: Either move `STRONG_SKILL_SCORE`/`PARTIAL_SKILL_SCORE`/`MIN_CONFIDENCE_SPREAD` into `test_matching.py` (their sole user) and soften the docstring, OR genuinely adopt them where applicable. For `MIN_LINKEDIN_TEXT_LEN`: import it in `test_pdf_parsing_quality.py:35` to replace the inline `5000`, or delete it if the PDF length threshold is conceptually unrelated. Don't change any asserted value.

## 5. `complete_json` stub kwarg style is inconsistent across the copies (`system=None` vs `*, system=None`)
- **Severity**: Medium
- **Category**: duplication (drift within the duplicated stubs)
- **File**: `test_match_reasoning.py:50` (`def complete_json(self, prompt, *, system=None)`), `test_campaign.py:55` (`*, system=...`) vs `test_weight_proposal.py:20`, `test_interview_scenario.py:46`, `test_devcase_design.py:22`, `test_seed_materializer.py:43` (all positional `system=None`)
- **Scenario**: While cataloguing finding #2 I read each stub body; the duplicated `complete_json` signatures have already diverged — some force `system` keyword-only (`*, system=None`), others accept it positionally. The real `ClaudeCliProvider` (which they claim to "mirror") has one signature; these stubs no longer agree on it. Evidence: side-by-side of the `def complete_json` lines listed above.
- **Root cause**: Copy-paste-then-tweak: each author adjusted the signature to taste because there was no single source of truth.
- **Impact**: A test that calls the provider with `system=` positionally passes against some stubs and would break against others — the stubs don't actually verify a consistent contract with production. This is a symptom that makes finding #2's consolidation more urgent (the shared stub would pin ONE signature matching the real provider).
- **Fix sketch**: Fold into the fix for #2 — the single shared `FakeProvider.complete_json` should match `ClaudeCliProvider.complete_json` exactly (check the real signature in `pipeline/jobfit/`), keyword-only `system` if that's what production uses. No standalone fix needed once #2 lands; listed separately because it documents existing drift to watch for during migration.
