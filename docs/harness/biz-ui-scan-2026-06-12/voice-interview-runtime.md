## 1. Give the candidate a real ending — the completed interview currently closes on a dead "Start again" button
- **Lens**: ui_perfectionist
- **Severity**: High
- **Category**: ui
- **File**: `app/_components/voice/VoiceInterview.tsx:666` (also `:252`, `app/api/interview/connect/route.ts:70`)
- **Scenario**: A candidate finishes the AI screen and clicks End. The page flips to phase `ended` — and re-renders the exact same pre-call panel: consent box still ticked, a fully enabled primary button now labeled "Start again" (`VoiceInterview.tsx:674`), and a gray "Ended" pill. No thank-you, no "what happens next". If they click the inviting button, `/connect` 409s and they end their interview staring at a red error: "This interview has already been completed."
- **Root cause**: `finalize(status)` knows completed-vs-failed (`VoiceInterview.tsx:214`) but discards it for the UI — both collapse into `setPhase("ended")` (`:252`), and the idle render path reuses the start button for `ended` (`:666-674`). The closing copy already exists (`messages/en.json:240-241` `interview.completedTitle/Body`, "A human recruiter will review the conversation and follow up") but only renders server-side if the candidate happens to reload the portal page (`app/interview/[token]/page.tsx:26-33`).
- **Impact**: Every successfully completed interview — the product's headline moment — ends on a misleading affordance whose only outcome is an error. The candidate's last impression of the employer is a dead button; "Start again" also implies the screen didn't count, inviting anxiety and support pings to the recruiter. For failed calls the retry affordance is correct, so the two outcomes must diverge.
- **Fix sketch**: Track the final status in state (e.g. `endedAs: "completed" | "failed"`) set inside `finalize`. On `completed`, replace the controls block with a closing card reusing the existing `interview.completedTitle/Body` strings (plus the existing moss/check visual language), hide the consent + start controls, and keep the transcript visible below. Keep "Start again" only for `endedAs === "failed"`. Pure client change; copy already in both catalogs.

## 2. Stop the "Interview in progress" button from revoking the live call and burying its transcript
- **Lens**: business_visionary
- **Severity**: High
- **Category**: functionality
- **File**: `app/features/sub_schedule/ScheduleTab.tsx:275` (also `app/api/interview/create/route.ts:38`, `app/_lib/db.ts:3781`)
- **Scenario**: A candidate is mid-call. The recruiter's Schedule card shows a button labeled "Interview in progress" — it reads as a status, but it is the same enabled `startInterview` action (`ScheduleTab.tsx:277-282`, label swap only at `:282`). One click: `/create` runs `revokeOpenInterviewSessions` which revokes `in_progress` sessions too (`db.ts:3784`), mints a fresh link, and emails the candidate a second invite — while they are still talking to the agent.
- **Root cause**: The shipped W6-4 reissue semantics ("a fresh link kills prior ones", `create/route.ts:32-38`) made the always-enabled button destructive for live calls, and nothing in `/create` distinguishes a stale link from an active conversation. Downstream, the hang-up still persists and scores (the `/complete` guard only excludes `completed`, `db.ts:3884`), but both recruiter reads surface the NEWEST session — the empty `created` one (`interviewStatusByEntries` first-row-per-entry by `created_at DESC`, `db.ts:3798-3812`; `latestInterviewByEntry` for the modal). So `hasTranscript` is false, the card shows "Start AI interview" again (`ScheduleTab.tsx:266`), the Interviewed section filter misses it (`:98-99`), and a completed, scored interview becomes invisible. Worsened by: a connect that never goes live latches `finalizedRef` without any `/complete` POST (`VoiceInterview.tsx:475-485`), so abandoned attempts sit `in_progress` forever, making this misleading button state common.
- **Impact**: A recruiter "checking on" a live interview can torpedo it: the candidate gets a confusing duplicate invite mid-call, and the finished transcript + scorecard vanish from every surface even though they exist in the DB — evidence loss at the Interview→Offer gate, and a trust-killing experience on both sides of the table.
- **Fix sketch**: (a) In `ScheduleTab`, render `in_progress` as a non-interactive status chip (reuse the live-pill pattern from `VoiceInterview`'s StatusPill) instead of an enabled button. (b) In `/create`, refuse (409, same hold-the-line stance as `/connect`'s guards) when the entry's latest session is `in_progress` with a recent `updated_at`, unless `force: true` — mirroring the repo's guarded-UPDATE conventions. (c) When surfacing per-entry status, prefer the latest session WITH a transcript over a newer empty one (one ORDER BY tweak in `interviewStatusByEntries`/`latestInterviewByEntry`).

## 3. Make the candidate's language hint actually reach the agent — it is dropped by both provider adapters
- **Lens**: business_visionary
- **Severity**: Medium
- **Category**: functionality
- **File**: `app/_lib/voice/elevenlabs.ts:19` (also `app/_lib/voice/openai.ts:85`, `app/api/interview/connect/route.ts:148`, `app/_components/voice/VoiceInterview.tsx:91`)
- **Scenario**: A Czech candidate opens the localized portal; the UI deliberately seeds the agent language from their locale (`VoiceInterview.tsx:91-93`, built for exactly this) and sends it to `/connect`. The agent still opens the interview in whatever language the provider defaults to — typically English — because the hint dies on the server.
- **Root cause**: `/connect` passes `adapter.connect({ instructions, language: language ?? session.language })` (`connect/route.ts:148`), but `ElevenLabsVoiceAdapter.connect()` takes no parameters at all (`elevenlabs.ts:19` — both `instructions` and `language` silently dropped; grounding rides only the browser-side prompt override), and `OpenAiVoiceAdapter.connect` destructures only `{ instructions }` (`openai.ts:85`) — `language` is a dead parameter, and the whisper-1 transcription config gets no language hint either (`openai.ts:98`). The browser-side ElevenLabs override sends only the prompt (`VoiceInterview.tsx:509-513`). The brief's mitigation — "Detect whether the candidate speaks Czech or English" (`interview-run.ts:59`) — cannot help the OPENING, because the agent speaks first, before there is anything to detect.
- **Impact**: For a Czech-market hiring product, the first words of its highest-stakes candidate moment are in an unpredictable language; a cs candidate greeted in English starts rattled, and Czech answers transcribed without a language hint degrade the very transcript the scorecard judges. The entire language plumbing (UI picker, `session.language` column, `coerceLanguage`) is currently decorative.
- **Fix sketch**: ElevenLabs: include `overrides: { agent: { language } }` in the existing `startSession` overrides object (return the session language from `/connect` beside `groundedPrompt`; the agent's allowed-overrides list must enable it, same caveat already documented for the prompt override). OpenAI: use the already-received `language` to append one sentence to `instructions` ("Open and continue in Czech unless the candidate switches") and set `audio.input.transcription.language`. No schema changes; the data is already on the wire.

## 4. Give the failed transcript save a retry path — the stash is write-only and the advice is false
- **Lens**: ui_perfectionist
- **Severity**: Medium
- **Category**: functionality
- **File**: `app/_components/voice/VoiceInterview.tsx:181` (also `:459`, `messages/en.json:272`)
- **Scenario**: The candidate finishes a 20-minute screen on flaky Wi-Fi; all three `/complete` retries fail. They see: "We couldn't save your interview. Please keep this tab open — your answers may not have been recorded." They dutifully keep the tab open… and nothing ever happens. The only enabled action is "Start again", which wipes the in-memory transcript (`turnsRef.current = []`, `:459-460`) — destroying the very data the message asked them to protect — and, for a completed session, then 409s anyway.
- **Root cause**: `persistTranscript` stashes the POST body in `sessionStorage` under `kp.iv.<sid>` (`:181-186`) but no code in the repo ever reads `kp.iv.*` back (single grep hit, the write site); there is no retry button, no background re-attempt, and the error copy promises a recovery flow that doesn't exist.
- **Impact**: The transcript is "the ONLY record of the interview" (the code's own words, `:174`) and it feeds the Interview→Offer scorecard. A transient network blip at hang-up silently costs the recruiter the whole screen and the candidate their effort — the worst possible failure of an async interview, currently handled with a dead-end message.
- **Fix sketch**: Hold the failed payload in state and render a "Try saving again" button beside the error (re-invoke `persistTranscript`; it already returns success). On portal mount, scan `sessionStorage` for `kp.iv.*` stashes and best-effort re-POST them (idempotent: `/complete` returns `alreadyCompleted` for duplicates and refuses empty-over-nonempty overwrites, so replay is safe by design). Soften the copy to match reality.

## 5. Decide the candidate portal's theme deliberately — it silently inherits the experimental Spark Dark register
- **Lens**: ui_perfectionist
- **Severity**: Medium
- **Category**: ui
- **File**: `app/layout.tsx:117` (also `app/interview/[token]/page.tsx:72`, `app/globals.css:181`, `docs/DESIGN.md:36`)
- **Scenario**: A candidate whose OS prefers dark (roughly a third of users) opens their interview link and gets the day-old "Spark Dark" register sight-unseen: sticker-shadow panels (the `[data-theme="dark"] .shadow-panel` ride at `globals.css:181` catches the portal's main call panel at `page.tsx:72`), the display face flipped to Bricolage, luminance-flipped status colors — with no way to switch, because `ThemeToggle` mounts only in the recruiter workspace sidebars (`Workspace.tsx:166`, `WorkspaceNav.tsx:85`).
- **Root cause**: The pre-hydration bootstrap applies `prefers-color-scheme` everywhere except `/landing` (`layout.tsx:117`, the only path exemption). DESIGN.md positions dark as "the playful sticker-sheet for creative users" of the studio and hard-exempts the landing as fixed art direction (`DESIGN.md:36-44`) — but the candidate portal, the most brand-sensitive EXTERNAL surface (a formal, recorded job interview), was never given the same decision. Recruiters QA the portal in the workspace's light register and have no idea a large share of candidates see a different, experimental one.
- **Impact**: Tone mismatch at the highest-stakes touchpoint: the "calm corporate studio" the design system prescribes for trust-building is replaced by a playful register the employer never chose and cannot preview per-candidate. Inconsistent brand presentation across candidates also undermines the comparability story the runtime works hard for elsewhere (same script, same agent — different look).
- **Fix sketch**: Extend the `THEME_INIT` path exemption to `/interview` (one line, identical precedent and enforcement comment as `/landing`) so candidate links always render Studio Light; note it in DESIGN.md beside the landing exemption. Alternatively, if dark is ever blessed for candidates, mount a visible toggle on the portal — but the one-line exemption matches the system's own "fixed art direction for external surfaces" logic and costs nothing.
