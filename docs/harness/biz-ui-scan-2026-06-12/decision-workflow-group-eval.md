## 1. Split human advances from automated advances in the audit attribution
- **Lens**: business_visionary
- **Severity**: High
- **Category**: functionality
- **File**: `app/_lib/decision-attribution.ts:16`
- **Scenario**: A recruiter clicks Advance on an AI-review card, in the analysis summary, or inline in the group eval (DEC3). In the Analytics Decision Log that decision renders with an **AUTO** badge, exports as "auto" in the CSV, and inflates the Automation panel's "Auto-advanced" tile — the recruiter's own judgment is credited to the machine.
- **Root cause**: Every advance — human and automated — writes the same `advanced` event kind (`app/_lib/db.ts:4189,4198` via `actOnPipelineEntry`, called by the human route `app/api/pipeline/[id]/route.ts:123` AND by `automation-pass.ts:230`, `automation-run.ts:187`, `offer-finalize.ts:49`). `DECISION_META` maps `advanced: { auto: true }` (`decision-attribution.ts:16`), and `summarizeAutomationImpact` counts ALL of them as `autoAdvanced` (`decision-attribution.ts:106` → rendered at `app/features/sub_analytics/AnalyticsTab.tsx:331`, badge at `DecisionLog.tsx:216-218`). Rejects already have the correct split (`rejected` human vs `auto_rejected` auto) — advances never got the mirror.
- **Impact**: The module's own contract says it: "in an auditable surface, defaulting … to AUTO would misattribute accountability to the machine — the most damaging default" (`decision-attribution.ts:53-54`, `DecisionLog.tsx:40-42`). The Decisions tab's entire pitch is AI recommendations behind human approval gates, yet the audit layer reports the human gate as automation. "Why was this candidate advanced?" gets the wrong actor; the auto/human filter chips (ANA5) and the automation-impact rollup are quietly wrong for the highest-volume positive decision.
- **Fix sketch**: Mirror the reject split, following the existing kind-based pattern: add an `actor` option to `actOnPipelineEntry` (default `"human"`), have the automation callers (`automation-pass.ts:230`, `automation-run.ts:187`, `offer-finalize.ts:49`) pass `"auto"`, and record kind `auto_advanced` for those — flipping `advanced` to `{ auto: false }` in `DECISION_META` and counting `autoAdvanced` from `auto_advanced`. Add the new kind to the `analytics.log.kinds.*` catalogs, `MOMENTUM_EVENT_KINDS` (`analytics-momentum.ts:25`), the funnel queries at `db.ts:2254,2339`, and the writer-coverage test in `decision-attribution.test.ts:35`. Historical rows stay ambiguous; attribution is correct going forward.

## 2. Thread the recruiter's locale through the group-eval narrative layer
- **Lens**: business_visionary
- **Severity**: Medium
- **Category**: user_benefit
- **File**: `app/features/sub_decisions/DecisionsTab.tsx:177`
- **Scenario**: A Czech recruiter opens the group evaluation. The modal chrome, comparison table, and wave rationales are Czech — but the AI head-to-head headline/keyPoints/recommendation, every per-candidate verdict/strengths/gaps/interview-probe, the topPick "why", and the Watch-outs panel all arrive in English. Worse, the SAME candidate's verdict shows in Czech on the Match tab (MAT1) and in English inside the group eval.
- **Root cause**: The locale plumbing exists at every layer but is never connected for this surface. `startTask("group_eval", …)` omits `lang` (`DecisionsTab.tsx:177`) even though the same component already threads `lang: locale` for interview prep at line 141 and holds `useLocale()` at line 28. Downstream, `runGroupEval` calls `runReasoning({ jobId, profileId })` with no `lang` (`group-eval-run.ts:328`) although `reasoning-run.ts:24-54` supports `lang` with a per-locale cache axis (MAT1); and `group_compare_cli.py:50` calls `generate(context, provider=provider)` without `lang`, leaving `generate()`'s `lang` parameter dead (`group_compare.py:148-157` — the system prompt even says "Write in the requested language"). The deterministic `risks`/`summary`/topPick-why templates are hardcoded English (`group-eval-run.ts:389-405,420`).
- **Impact**: The flagship comparative-decision surface breaks the product's bilingual differentiation exactly where the recruiter forms the hire/reject verdict, and it's inconsistent with the already-localized Match tab. The capability is fully built (prompt directive, locale cache, CLI precedent `--lang` in match_reasoning) — it ships dark for this surface.
- **Fix sketch**: Pass `lang: locale` in the group_eval task params; in `runGroupEval` forward it to each `runReasoning` input and add a `--lang` flag to `group_compare_cli.py` (mirroring `match_reasoning_cli`), passing it to `generate(context, lang=lang, provider=provider)`. For the deterministic `risks` strings, reuse the DEC4 reason-code pattern (`screen-wave.ts:34-42` → `decisions.wave.reasons.*`): persist `riskCode + params` beside the English string and render from `decisions.groupEval.risks.*`. Saved evals keep their language until re-run — the existing `createdAt`/re-run affordance covers staleness.

## 3. Show the committed wave's per-candidate outcomes, not just a count banner
- **Lens**: ui_perfectionist
- **Severity**: Medium
- **Category**: functionality
- **File**: `app/features/sub_decisions/ScreenWaveModal.tsx:161`
- **Scenario**: The recruiter tunes the dry-run preview, clicks "Reject & notify N", and the whole decision list disappears — replaced by a one-line banner ("Rejected X of Y, kept Z"). Who was actually rejected, who was skipped because their stage changed mid-wave, and which rejections failed to notify (beyond a bare count) are all hidden at the exact moment the action became irreversible.
- **Root cause**: The committed branch renders only the banner (`ScreenWaveModal.tsx:161-175`); the rejects/keeps lists live exclusively in the not-committed branch (:227-255). The code clearly intended otherwise: `view = committed ?? preview` (:113) computes the lists from the committed result, and `reasonText` branches on `view?.dryRun` to pick "did" phrasing (:125) — but `reasons.rejectDid` and `reasons.staleSkipped` (en.json:786,788, cs.json:786,788) are unreachable, because `staleSkipped` decisions only ever exist in committed runs (`screen-wave.ts:196-199`) and the preview is always `dryRun:true`.
- **Impact**: The commit can legitimately differ from the preview the recruiter approved — the CAS skips candidates whose stage changed mid-wave (`screen-wave.ts:195-199`) and comms can fail per candidate (:208-215) — and the UI hides exactly those deltas. Trust in the product's one irreversible batch action depends on verifying what it just did; today the recruiter must dig through the Analytics Decision Log.
- **Fix sketch**: Render the existing rejects/keeps sections in the committed branch too (the data and localized `reasonText` already work — `staleSkipped` keeps surface in the keeps list with their amber rationale). For comms, extend `ScreenDecision` with a `commsFailed?: boolean` set in the catch at `screen-wave.ts:210-215` and badge those rows ("notification failed — nudge manually"), turning the bare `commsFailures` count into an actionable list. No new API or state.

## 4. Stop faking success when a group-eval decide lands on nothing
- **Lens**: ui_perfectionist
- **Severity**: Medium
- **Category**: functionality
- **File**: `app/features/sub_decisions/GroupEvalModal.tsx:191`
- **Scenario**: A recruiter reopens a cached group eval. A candidate who was meanwhile rejected by a screening wave (or decided from another surface) still shows live Advance/Reject buttons. Clicking Advance flips the tab badge and pill to a green "Advanced" — but nothing happened: the candidate is no longer in the pending pool. Likewise, when a stale decide hits the 409 CAS in the queue, the card slides out, silently reappears after the reload, and the modal pill still claims success.
- **Root cause**: `decide()` sets the `decided` pill unconditionally BEFORE invoking the callback (`GroupEvalModal.tsx:193-196`), while `DecisionsTab`'s `onDecide` silently no-ops when the identity no longer resolves to a live entry (`DecisionsTab.tsx:346-349 — "Acts only on still-pending entries"`), and `act()`'s catch swallows every failure (409 or 500) with only a queue reload — no user-visible message (`DecisionsTab.tsx:144-151`). The cached `evaluation` snapshot never refetches (:188-190), so the modal has no idea who is still actionable.
- **Impact**: A green "Advanced" pill for an action that never executed is the worst kind of feedback on a hiring decision — the recruiter walks away believing the candidate moved. The silent 409 reappearing-card has the same trust cost on the queue cards.
- **Fix sketch**: Make `act()` return a success boolean (it already distinguishes the paths) and have `onDecide` return `false` for unresolvable identities; in the modal, flip the pill only on success and otherwise show the existing amber notice pattern ("This candidate was already decided elsewhere — re-run for a fresh comparison", reusing the `Notices` styling at :347-353). Better: derive actionability up front — pass the live pending entry ids (`evalGroup.entries`) into the modal and render departed candidates' action area as a neutral "decided elsewhere" pill instead of live buttons. For queue cards, surface a transient `role="status"` message on 409 ("Queue changed — refreshed") next to the existing `error` alert seam (:260-262).

## 5. Give Re-run an in-content progress state instead of a footer-only label swap
- **Lens**: ui_perfectionist
- **Severity**: Low
- **Category**: ui
- **File**: `app/features/sub_decisions/GroupEvalModal.tsx:219`
- **Scenario**: The drift notice tells the recruiter "2 candidates changed since this ran — re-run". They click Re-run. For the next while (ranking + up to 6 parallel LLM reasoning calls + the compare narrative, `group-eval-run.ts:308-334,399`), the only change anywhere is the footer button reading "Generating…" — the stale table, fairness matrix, and tabs stay fully interactive with the old `ranAt` subtitle, and the drift warning that prompted the click keeps showing. Recruiters keep reading (and can keep deciding from) the comparison they were just told is stale, then the content swaps under them without transition.
- **Root cause**: `loading` gates only the footer button (`GroupEvalModal.tsx:219-227`) and the full-body spinner is reserved for `loading && !evaluation` (:230); a re-run keeps `evaluation` set (`DecisionsTab.tsx` only clears it via `openGroupEval`'s reset when reopening, not visibly during in-modal re-run — the cached payload stays rendered until the task result lands at :107-110).
- **Impact**: The re-run affordance is the product's own staleness remedy; giving it no visible progress on a multi-second-to-minute pipeline makes the modal feel unresponsive and leaves stale data implicitly endorsed while a fresh ranking is being computed.
- **Fix sketch**: While `loading && evaluation`, dim the body (`opacity-60 pointer-events-none` on the content wrapper) and show a compact inline progress row at the top reusing the existing `Loader2 + t("generatingFull")` pattern (:231-233); swap the drift notice for "Re-running with the current pool…" so the prompt and the action don't contradict. Honors the existing reduced-motion and aria-live conventions; no new state — `loading` and `evaluation` already encode the condition.
