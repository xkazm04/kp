## 1. Add a supervised mode so the clock queues auto-rejects for approval instead of emailing candidates unattended
- **Lens**: business_visionary
- **Severity**: High
- **Category**: feature
- **File**: `app/_lib/automation-pass.ts:237-263`
- **Scenario**: The manual "Run pass" button earned a mandatory look-before-commit preview (AUTO3, `PassPreviewModal.tsx`) precisely because the pass auto-rejects AND emails real candidates in one breath. But the scheduled clock (`instrumentation.ts:31-36` → `scheduler.ts:32` → `runAutomationPass()`) applies those same rejections sight-unseen every 15 minutes. A hiring manager's only autonomy choices are "fully autonomous rejections" or "clock off" — there is no middle rung on the trust ladder.
- **Root cause**: `executeAutomationPass` applies `d.action === "reject"` directly (`automation-pass.ts:244-247` — `actOnPipelineEntry("reject")` + `dispatchRejection(..., { automated: true })`). The scheduler row (`scheduler-store.ts:32-40`) has `enabled` and `interval_minutes` but no autonomy-level knob; the dry-run gate exists only on the manual route (`app/api/automation/run/route.ts:13-14`).
- **Impact**: This is the single biggest blocker to a recruiter ever switching the clock ON for a live req — automated rejection is the one irreversible, candidate-visible action, and the product's marquee "autonomy control room" offers no "compute it, I'll click it" mode. Progressive trust (advances automatic, rejections approved) is also the posture EU recruiters expect for fully automated adverse decisions (GDPR Art. 22 optics in the Czech market).
- **Fix sketch**: Add a `reject_mode` (`auto` | `approve`) column to the `scheduler` row (additive ALTER like AUTO2's `decisions_json`, `scheduler-store.ts:55-59`) surfaced as a third control in `SchedulerControl`. In approve mode, the apply loop downgrades each fairness-cleared reject to `setApproval(d.entryId, "rejection_review", JSON.stringify(d))` — registering `rejection_review` in `APPROVAL_KINDS` (`app/_lib/approval-kinds.ts:9-15`) routes it onto the existing Decisions gate, and `evaluate_entry` already freezes entries with a pending approval (`pipeline/jobfit/automation.py:173-174`), so a queued candidate can't be re-actioned next tick. Default `approve` for new installs; advances/holds/alerts stay autonomous.

## 2. Record a per-entry comms-failure marker when an auto-reject's notification fails — today the candidate is silently ghosted
- **Lens**: business_visionary
- **Severity**: Medium
- **Category**: functionality
- **File**: `app/_lib/automation-pass.ts:244-247,273-281`
- **Scenario**: The policy pass rejects a candidate (DB transition commits) and then `dispatchRejection` throws (`comms-dispatch.ts:132` — `sendComm` is the step that may fail). The candidate is out of the funnel but was never told; the recruiter sees only `errors: 1` in the run summary with no pointer to *who* needs a manual nudge.
- **Root cause**: The per-decision catch (`automation-pass.ts:273-281`) only prefixes `d.reason` with "Apply failed:" and bumps `summary.errors`. Unlike the screening wave — which handles the identical failure with a per-entry `rejection_comms_failed` audit event reading "Auto-rejected, but the notification failed to queue — nudge manually" (`app/_lib/screen-wave.ts:208-215`, event kind already registered in `decision-attribution.ts:41`) — the pass writes no pipeline event, so nothing surfaces in the activity feed or the candidate drawer history. Bonus accounting bug: `summary.rejected += 1` sits AFTER the `await dispatchRejection` (`automation-pass.ts:246-247`), so a rejected-but-unnotified candidate is not counted as rejected — the run log says `0 rejected, 1 error` for a pass that genuinely rejected someone.
- **Impact**: Ghosting is the #1 candidate-experience complaint about ATS automation, and KP's own `dispatchRejection` doc-comment promises it "never ghosts a rejected candidate". The audit trail (the trust differentiator) also under-reports rejections whenever the comm hop fails.
- **Fix sketch**: Mirror screen-wave: move `summary.rejected += 1` directly after the successful `actOnPipelineEntry`, wrap only `dispatchRejection` in its own try/catch, and on failure `recordAutomationEvent(d.entryId, "rejection_comms_failed", ...)` + keep counting it in `summary.errors`. The event kind, attribution tone, and wording all exist — reuse them.

## 3. Make the decision log distinguish applied / failed / skipped — failures currently render as successes and skips vanish
- **Lens**: ui_perfectionist
- **Severity**: Medium
- **Category**: ui
- **File**: `app/features/sub_pipeline/SchedulerControl.tsx:348,374-391`
- **Scenario**: A recruiter expands a run in the AUTO2 history panel. A decision whose apply *failed* (caught at `automation-pass.ts:273-281`, action left as `reject`/`advance`) renders with the same confident coral REJECT / moss ADVANCE badge as a decision that actually landed — the only clue is "Apply failed:" buried mid-prose. Meanwhile a CAS skip ("stage changed mid-pass — no rejection email went out", downgraded to `action: "none"` at `automation-pass.ts:233-235,248-253`) is filtered out of the list entirely by `acted = decisions.filter((d) => d.action && d.action !== "none")` (`SchedulerControl.tsx:348`). In the preview, a fairness-backstop-blocked reject (`automation-pass.ts:254-263`) is indistinguishable from a routine hold: `PassPreviewModal` never reads `d.alerts` (its `PreviewDecision` type at `PassPreviewModal.tsx:8` doesn't even carry the field) and files it under the collapsed "held" `<details>` (`PassPreviewModal.tsx:101-115`).
- **Root cause**: The badge style is keyed solely on `d.action` (`SchedulerControl.tsx:376-383`); outcome state (applied vs failed vs skipped vs fairness-refused) lives only as English prefixes inside `d.reason`, and the row filter treats audit-relevant anomalies ("none" = near-miss the CAS prevented) as noise.
- **Impact**: The run history is the product's audit-trail showpiece, and it visually misclassifies exactly the rows an auditor cares about: actions that failed look done, actions that were prevented look like they never happened, and fairness interventions (the FAIRNESS_BLOCKED_REJECT_ALERT regression signal, `automation-pass.ts:21`) hide among ordinary holds.
- **Fix sketch**: Add an explicit `outcome: "applied" | "failed" | "skipped" | "fairness_blocked"` field to `AutomationDecision` set at each branch in `executeAutomationPass` (additive — persisted `decisions_json` stays backward-compatible; derive from the reason prefix for old rows). Render failed rows with the existing coral error treatment + XCircle, show skipped rows (distinct muted style) instead of dropping them, and give fairness-blocked rows an AlertTriangle accent in both the history list and the preview modal's reject section.

## 4. Localize policy-pass decision reasons — the cs recruiter reads an English audit trail while screen-wave already solved this (DEC4)
- **Lens**: ui_perfectionist
- **Severity**: Medium
- **Category**: ui
- **File**: `pipeline/jobfit/automation.py:157-197`
- **Scenario**: A Czech recruiter opens the pass preview or run history: chrome, badges, and counts are Czech (via the `pipeline.scheduler`/`pipeline.tab` catalogs), but every per-candidate reason — "BAU score 35 < 40", "early-career: human screening gate (never auto-advance/reject)", "accepted; awaiting match score", plus the TS-composed "Apply failed:"/"Skipped: stage changed mid-pass" prefixes and fairness verdicts (`automation-fairness.ts:48-66`) — is English prose, rendered verbatim in `PassPreviewModal.tsx:80,94,110`, `SchedulerControl.tsx:390`, and the activity feed (alerts persist `d.reason` as event detail, `automation-pass.ts:267-272`).
- **Root cause**: `evaluate_entry` emits free-form English f-strings only. The repo already established the fix pattern for exactly this surface: screen-wave's DEC4 ships a structured `reasonCode` + `reasonParams` mirror alongside the byte-pinned English audit string, and the modal renders `decisions.wave.reasons.<code>` localized (`app/_lib/screen-wave.ts:22-42,48-62`) — the policy pass never adopted it.
- **Impact**: The decision log is the half of the product a Czech hiring manager scrutinizes hardest, and it reads half-translated — undercutting both the dual-locale promise (the i18n catalog waves are an active investment, cf. commit b6ee6b9) and the polish of the trust surface. It also blocks ever localizing reasons retroactively, since only prose is persisted in `decisions_json`.
- **Fix sketch**: Have `evaluate_entry` return `reasonCode` + `reasonParams` next to `reason` (closed set: ~10 codes covering its branches); thread them through `AutomationDecision` and the TS downgrade paths (codes for `applyFailed`, `staleSkipped`, `fairnessBlocked` with the original code nested in params). Render via a `pipeline.scheduler.reasons.*` catalog in the preview modal + run history with fallback to the English `reason` for unmapped/legacy rows — exactly the screen-wave contract, so the persisted English audit string stays untouched.

## 5. Show when the next scheduled pass will fire — the clock hides its own countdown
- **Lens**: ui_perfectionist
- **Severity**: Low
- **Category**: ui
- **File**: `app/features/sub_pipeline/SchedulerControl.tsx:25-30`
- **Scenario**: The control bar shows ON, "every 15 min", and "last auto run 9 min ago" — the recruiter who just enabled the clock (or shortened the cadence) has to mentally add the interval to the last run to know whether/when automation will next touch their board. "Is it armed, and when does it act?" is the basic operator question the bar never answers.
- **Root cause**: `nextDueAt` is computed and persisted by the store (`scheduler-store.ts:86`, recomputed on toggle/interval change at `:131,156-160`) and already shipped to the client on every GET — `schedulePayload()` returns the full `getSchedule()` (`app/api/automation/schedule/route.ts:17-24`) — but the component's local `Schedule` type (`SchedulerControl.tsx:25-30`) omits the field, so it is silently dropped.
- **Impact**: Missing the one forward-looking signal makes the clock feel like a black box right after the highest-anxiety moment (enabling it); it also hides cadence anomalies (e.g. a forced run pushing the window out) that `nextDueAt` would make legible.
- **Fix sketch**: Add `nextDueAt: string | null` to the client type and render "next pass {relativeTime}" beside `lastAutoRun` (the existing `useRelativeTime` from `PipelineShared` already handles future timestamps' phrasing or can be trivially extended); when disabled show nothing, mirroring the store's `next_due_at = null` contract. Two strings in the en/cs `pipeline.scheduler` catalog.
