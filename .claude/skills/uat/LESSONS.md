# Lessons — uat

Methodic lessons from real runs. Append-only; newest at the bottom.
Entry format: `## <version-used> — <YYYY-MM-DD> — <project>` then bullets.
A `### Redesign proposal` sub-block signals a major-bump candidate.

## 1.0 — 2026-08-10 — CandiDate
- Grounding scores from parallel L1 characters are not comparable: each character enumerated their own context-source list, so one surface scored 8/10, 15/16 and 5/8 in the same run — three different rulers, not a trend. Applied in v1.1: each AI surface's grounding-source list is defined ONCE in the overlay and every character scores against that shared denominator; per-character extras are recorded as named additions, never silent denominator drift.

## 1.1 — 2026-08-10 — CandiDate
- **Convergence is not coverage — it can actively mask a sibling defect.** Three parallel L1 walkers independently found the same bug in one branch of a shared mapping function (`countFor`, a three-way switch feeding three collapsed-column badges). The ×3 convergence correctly ranked it above impact arithmetic — and gave everyone false confidence that the function had been *audited*, when in truth all three had read exactly one branch and stopped. L2 folded a second column and found the sibling branch badging `0` over a fully populated panel. Applied in v1.2: when an L1 finding lands inside a shared switch/map/lookup that serves sibling cases, the walker must enumerate **every** branch against live-shaped data before emitting, and convergence explicitly does NOT discharge that duty.
- **An L1 finding scoped to a degraded/alternate code path needs its environment precondition declared, or L2 cannot honour it.** Two majors here were scoped to the app's *keyless* (no-API-key) deterministic path. The L2 host had a live key, so that path was structurally unreachable — discovered mid-run, after the browser time was already committed. The correct verdict was `uncertain — not reproducible on this host`, not `refuted`, and the run had to say so three times. Applied in v1.2: `l2_priority` carries an explicit environment precondition (keys present/absent, plan tier, project type, locale), L2 preflights those against the live environment *before* driving, and any precondition it cannot satisfy yields `uncertain` with the reason — never a silent pass or a refutation.
- **A control arm turns a plausible AI-grounding finding into a proof, cheaply.** The strongest evidence this run produced was one extra 30-second session: identical opening sentence, attachment removed. With the attachment the brief's title was lifted verbatim from it; without, the model synthesised its own. That single control converted "the model probably mined the attachment" into a causal demonstration — and incidentally widened the finding (both arms stamped the title `inferred`, so the defect was not attachment-specific at all). For any L2 claim of the form "the AI used input X", running the same prompt minus X is nearly free and should be routine.
- **Refute your own mid-run scares with a control before filing them.** A Czech transcript stored as mojibake looked like a UTF-8 defect; the same sentence through the real UI stored perfectly, exposing the driver's shell payload as the culprit. Filed as an explicit `refuted` finding so a future run does not re-raise it. Recording refutations is as valuable as recording findings — it stops the same ghost costing browser time every quarter.

## 1.2 — 2026-08-10 — CandiDate (drain — folded into the v1.2 package)
- **The findings schema did not carry what the drain's section 1 needs.** `drain` §1 is defined as "what went finding → fix → `resolved-verified`, each with its `ceiling`" — but the run being drained had **zero** `resolved-verified` rows and one `ceiling` (on a *refuted* finding), despite every prior major genuinely being fixed and re-verified. The re-certification had been recorded as a *strength* row per Character ("the loop closed, ids cited at the fix sites") plus prose tables in three separate reports, with the ceilings scattered across those reports, `SUMMARY.md`, and the previous run's recertify document. §1 had to be reconstructed by hand from five sources, and the ceilings→§2 pipeline — the drain's main input — silently broke. Applied in the v1.2 package: a run that re-certifies prior findings must carry those ids forward into its own `findings.json` with `resolution` + `ceiling`; the drain records the miss in §3 if it has to reconstruct.
- **L2 must re-score the findings it widens, not just narrate the widening.** The L1→L2 handoff itself worked exactly as designed (every `l2_priority: high` item got a live answer; both "new at L2" findings sat in the class the handoff structurally cannot cover). Its blind spot is the return leg: L2 turned "an attachment-mined title goes unchipped" into "the title is inferred by default in *every* session, attachment or not", and "two look-alike postings" into "two byte-identical twins" — and both widenings existed only in report prose while `findings.json` still held the L1 `impact`. A drain ranking off the JSON would have under-ranked the run's strongest evidence. Applied: L2 updates `impact`/`severity` on carried findings and preserves `impact_l1`/`severity_l1` so the delta is machine-visible.
- **Voice sections changed the *ranking*, not only the framing — and only because they were written twice.** The most decision-useful sentence of the run („Nástroj, který mi o sobě tvrdí, že nic nemá, když toho má plno, mě učí své vlastní UI ignorovat. A to je horší než chybějící funkce, protože to podkopává i to, co funguje.") has no finding row above *minor*, and it moved a badge bug from tenth to third in the design backlog. The signal was the **escalation between the two voices**: at L1 the same Character called it a *drobnost*; at L2, having actually folded the panel, she called it corrosive. Applied: the drain ranks by voice-claimed dimension when a voice escalates above its row severity, and a run appends the L2 voice rather than replacing the L1 one.
- **Recurrence is stronger evidence than severity, and nothing expressed it.** The sharpest line in the run was not about a defect: *"it is the same two handles as last time — which, after two runs, starts to read as a decision rather than a backlog."* An item that survives a full run→drain→ship→recertify cycle unbuilt and returns unchanged has cost that Character trust twice; a first-time major has cost it once. Applied: findings carry `recurrence` (consecutive cycles raising the same unbuilt gap) and the drain ranks it first, above convergence and above impact arithmetic.

## 1.2 — 2026-08-10 — ascent (first run of v1.2 on a second project)

- **`init` has no guard against an overlay that already exists, and the caller is often the one who is wrong.** This run was commissioned as ascent's "first UAT outing", with an `init` authoring three fresh Characters. ascent already had **30 Characters, 11 journeys and 5 prior runs**; only the *engine* was new (v1.2 installed the same day). An obedient `init` would have written a second parallel cast into a repo that already had one, and every future run would have had two rosters with no comparable scores. The overlay is the durable asset and the skill was the thing most likely to damage it. Applied in v1.3: `init` step 0 checks `uat/characters/`, `uat/journeys/`, `uat/runs/` and switches to `update` regardless of how the run was commissioned, recording the corrected framing in the run brief.
- **An unsatisfiable environment precondition is usually two minutes of work away from being satisfiable — try to BUILD the arm before resolving `uncertain`.** v1.2 (correctly) added "declare the precondition, preflight it, resolve `uncertain` if unmet". Applied literally that becomes a way to *avoid* the hardest findings. The run's second-ranked finding — the advertised free no-signup public scan returning `401` — was filed at L1 as unreachable because the UAT host ran `ASCENT_AUTH_BYPASS=1`. Restarting the dev server with the bypass off took two minutes and converted it into a confirmed blocker with live evidence, and *widened* it (every read-only surface stays open anonymously; only running a scan is walled — the one action a buyer needs). By contrast a forecast fixture genuinely could not be built (the seeders scan in a single pass, so no org can ever produce a forecast), and saying that precisely — with the fixture that *would* close it — was the right answer there. Applied in v1.3 as L2 step 0: build first, `uncertain` as fallback, and always name the fixture that would close it. **Corollary, also applied:** the overlay's own convenience flags (auth bypass, opened dashboards, disabled quotas) are the likeliest thing silently invalidating a Character — they put every walker in a state no real user of that segment occupies, and out-of-segment Characters are exactly who they invalidate. Here the "anonymous buyer" was being driven as a signed-in user with an org name in the header, and nothing flagged it.
- **The run brief is written by the one participant nobody reviews, and parallel walkers read it as fact.** The orchestrator primed Dana's walker with a "recurrence lead" asserting that `briefing.ts:393` rendered a trajectory headline *unconditionally* — the guard sat two lines above, missed in a skim. That is confirmation bias injected straight into the design that exists to avoid it: a walker sent to confirm a fixed bug will generally confirm it. Retracting mid-run cost one message, and the walker — explicitly told to re-derive and contradict — produced something better than either version: the partial fix nulls `forecastConfidence` on `lowData`, so the hedge is **omitted rather than replaced**, and a bare dated ETA reads *more* confident than the hedged one it replaced. It also held `recurrence: 2` against the orchestrator's retraction, with evidence. Applied in v1.3: orchestrator-authored leads must be labelled `HYPOTHESIS — verify independently, and contradict me`, or verified before dispatch.
- **Not recorded as a method change, but worth knowing: the machine-readable artifact is the one that silently goes missing.** Three of ascent's five prior runs have no `findings.json` at all — including the largest and most recent (30 Characters, 2026-07-16), which produced rich prose and nothing a drain could rank. Its own footnote records why: the synthesis subagent's attempt to write the file was **blocked by its tooling policy**, and a `runId` reached the script as `undefined` so every artifact landed in `runs/undefined/`. This run hit the same write-policy wall from the *orchestrator* seat on `SUMMARY.md` and routed around it with a small emitter script. v1.2's lesson about carrying `resolution`/`ceiling` forward into `findings.json` quietly assumes the file gets written at all. **A run must not depend on a single privileged write path for its only machine-readable output** — build `findings.json` from the per-Character reports programmatically (a 30-line extractor over the fenced ```json blocks did it here) rather than hoping one agent writes it correctly.

## 1.2 — 2026-08-10 — CandiDate (recertify; recorded in kp under a library-version conflict, folded here by the orchestrator as the v1.4 package)
- **`recertify` never asserts that the running app actually contains the commits it is certifying — and that is the one assumption the whole mode rests on.** This run nearly emitted a fabricated i18n regression against a Character's explicit language criterion: the English UI rendered three **raw i18n keys** (`checkbox "library.tab.intake.promoteMarket"`), all of them strings the commits under test had added, while the identical Czech arm rendered every one translated and the message file held both at the same paths. Cause: the dev server had been up since 13:43, the commits landed 14:28–14:38, and next-intl loads messages with a **per-locale cached dynamic import** — so the components hot-reloaded but the *English catalogue did not*. The trap is worse than it sounds because it fails **asymmetrically**: the locale first compiled *after* the fix looks perfect, so a single-locale run sees nothing and a two-locale run reads it as a shipped defect. `touch` did not bust the cache; only a restart did. v1.1's env-precondition rule doesn't cover this — that rule is about a *finding's* scope (keys absent, plan tier, flag off), whereas this is about the *environment's freshness relative to the diff*. **Proposed for the next library version:** `recertify` step 0 — compare the server process's start time against `git log -1 --format=%ci` for the commits under test and restart if it is older; a long-lived dev server is the default state on a machine where the fixer and the certifier are different sessions, so this will recur everywhere, not just here.

- **The carry-forward rule works, but "carry those ids forward into ITS OWN `findings.json`" is undefined for `recertify`, which has no run id of its own.** The rule was written from a `run`'s point of view and it did exactly its job here — the pull to record ceilings as prose in the three Character reports was strong (that is where the voice lives), and having a schema field to fill is what stopped it; the run ended with 5 `resolved-verified` rows and 7 `ceiling`s in machine-readable form, which is precisely what the last drain lacked. The ambiguity is only about *where*: `recertify` re-runs "only the affected character × journey" and produces "a diff report, not a full re-sweep", so it has no `runs/<id>/` of its own. I updated the **originating run's** `findings.json` in place (adding `recertified_in`, `recertify_evidence`, `ceiling`, and appending the new/refuted rows) and wrote `recertify.md` beside it. That kept one findings table per journey-run rather than splitting the truth across two — but it was a judgement call the skill should make for the next session instead of leaving each run to invent it. **Proposed:** state it explicitly in `Mode: recertify` — recertify writes back into the originating run's `findings.json` (never a new one), stamping each carried row with the recertifying commit range, and appends `recertify.md` to the same run directory.

- *(Not a lesson, an observation worth keeping)*: re-reading the **prior run's transcripts back out of the live DB** and replaying them verbatim made the two arms genuinely comparable — same words, one variable — and it is cheaper than re-authoring stimulus. Worth doing whenever a recertify has to re-drive a stochastic surface. It also produced the run's sharpest evidence: with the attachment the title was the attachment's, without it the engine produced **no title at all**.

## 1.4 — 2026-08-10 — CandiDate (closing the recertify's NEW findings — recorded, not applied)
- **`recertify` produces findings with no door into the backlog.** `drain` is defined over a *run*; `recertify` writes back into that run's `findings.json` (v1.4's own rule) and can leave three kinds of row the drain never saw: a **re-scored** one (`L2-NEW-2`, minor → major, `recurrence: 2`), a **still-open** one whose shipped fix touched only its compounding clause (`L1-TOM-5`), and a **new** one *introduced by a fix under certification* (`L2-RC-1`). None of them is a run, so nothing triages them, and the insights doc + `BACKLOG.md` — the two documents the builders actually read — silently stop being the whole picture the moment a recertify lands. Handled here by appending a **"recertify delta"** section to the existing insights doc (same rules: cite finding id + Character voice, triage build/concept/decline, tally) and a matching sub-section under the run's `BACKLOG.md` heading, continuing its numbering. **Proposed:** make that the defined tail of `recertify` — a delta triage against the drain it inherits — rather than a fourth mode.
- **A finding's `got` is a symptom; `recertify` does not owe a root cause, and the drain's "what to build" is a guess until someone gets one.** The drain's build item for `L2-NEW-2` said "tighten the extraction contract so a confirmed hard condition lands as a graded requirement" — reasonable, prompt-shaped, and only half the defect. Reading the **stored briefs of all five live sessions** (not the prompt) showed the contract offered *two homes for the same fact and ranked neither*: `dealbreaker_context` sat in the suggested facet vocabulary while `requirements` was described only as a *grading* rule, so the model filed every hard condition as facet prose — and the promote gate then read a narrower slice of the brief than the brief actually held, which is why an escalated *representational* finding turned out to *block the job*. The fix had to be two-ended (route it in the contract **and** read it deterministically wherever it already landed), and only the deterministic end is testable without a key. **Proposed:** where a drain item's "what" is a hypothesis about model behaviour, say so — and make the builder's first step reading the stored artifacts of the failed sessions, not the prompt.

## 1.4 — 2026-08-10 — ascent (first DRAIN of this project — recorded, not applied; local copy is v1.2, library is v1.4, so the version conflict is noted rather than resolved by an edit)

- **The drain's output locations are per-app by design, and no mode ever writes them — so a project can accumulate five undrained runs without anything looking broken.** `Mode: drain` ends with "where the artifacts live is per-app (the overlay documents it — analysis doc home, backlog file, concept-doc home)", but `init`/`update` scaffold `characters/`, `journeys/`, `rubric.md`, `env.md`, `accepted-gaps.md`, `driver/` and `runs/` — never those three paths. ascent's `uat/README.md` documented the run layout in a table and was silent on all three, and its five prior runs (2026-06-19 ×2, 06-20, 07-16 sweep + recertify) produced rich Character prose and **zero triaged backlog items**; the 07-16 sweep was 30 Characters. The failure is invisible because each run's own artifacts look complete — the missing thing is downstream of the run and nobody owns it. **Proposed:** `init`/`update` write the three destinations into the overlay README (defaulting to `docs/product/uat-insights/<run-id>.md`, the repo's tracked backlog, and the owning feature-doc dir) and `drain` refuses to start until they resolve. The general shape is worth naming beyond this skill: *a contract clause that delegates a decision to a per-app file, without any mode being responsible for writing that file, is a clause that silently never executes.*

- **Two Characters can reach OPPOSITE verdicts on the same evidence, and the drain's ranking rules only know how to handle agreement.** Convergence ("multiple Characters independently") ranks an item UP. Here the ~8% prompt-coverage cap was filed by Sam as `SAM-L1-07` and independently **acquitted** by Tomáš — *"the model isn't reading 8% of the repo and guessing; it's narrating a fully-computed signal set and sampling 22 KB for texture… The pitch survives"* — after he did the arithmetic Sam did not. Nothing in the ranking order covers a contested finding, and the naive readings are both wrong: counting it as convergence-of-one inflates it, dropping it loses the ceiling. The disposition that worked was to **decline the defect, keep the ceiling, and split out the sub-claim both agreed on** (the confidence chip measures *fetch* coverage, not *prompt* coverage — that half became a build item). **Proposed:** add a contested-finding rule to `drain` §2 — when Characters disagree on the same evidence, rank by whose reasoning engaged the mechanism rather than by count, record the loser as `decline-with-reason` carrying the winner's arithmetic, and check whether a narrower sub-claim survives the disagreement. A disagreement is *stronger* evidence than a lone finding, not weaker — it means two lenses were pointed at the same object.

- **A Character's PROCESS ask has no shape in build / concept-doc / decline, and forcing it into one loses it.** Dana's fourth ask was not a defect: *"someone in my role needs to read that PDF end to end before it ships again. Not test it — read it, out loud, as if to a board."* There is no human in this loop to assign that to — which is the premise of the repos this skill runs in. Filing it as `build` invents a ticket nobody can execute; declining it silently discards the sharpest process observation in the run. It was recorded as a fourth disposition, a **standing method commitment** ("any change to the briefing PDF re-runs Dana's journey before merge"), written into the backlog's guardrail block beside the strengths — and it is, accurately, what `/uat` L2 already is: this run was the first time anyone read that PDF end to end, and it produced the drain's #3 and #10. **Proposed:** name `method-commitment` as an explicit fourth disposition in `drain` §2, so a Character's ask about *how the team works* lands somewhere durable instead of being rounded to a ticket or a decline.

## 1.4 — 2026-08-10 — workspace (v1.5 fold — orchestrated cycle 3, CandiDate + ascent)
- Five lessons from the drain-and-execute cycle applied as v1.5: (1) drain-artifact homes are written by `init`/`drain` themselves — delegating them to a per-app file no mode writes left five runs undrained in one repo; (2) recertify-born findings get a `## New findings for the next drain` section in recertify.md and drain reads it — they previously had no door into the backlog; (3) a build item's root cause is labelled `hypothesis` until verified against the failing runs' stored artifacts (the requirements[] root cause was findable only in the stored briefs, and was a different defect than the prompt-reading theory); (4) opposing Character verdicts on the same evidence are a first-class finding (segmentation decision), never averaged; (5) `method-commitment` joins build/concept-doc/decline as a fourth disposition — process asks have no shape in the other three.

## 1.5 — 2026-08-17 — CandiDate (analytics-consolidation run; applied as v1.6)

- **The highest-value L1 finding class is not "missing" — it is "present, correct, tested, and wired to nothing", and one grep detects it.** This run's entire headline was that class. A prior blocker (`KAT-L1-001`, calibration validating a score against outcomes the score itself caused) had been *fixed well*: the route now computes a per-source `leakage` object naming its own circularity — level, code, note, and a ceiling reading "treat this curve as internal consistency, not accuracy". `grep -rn leakage app/features/` → **0 hits**. The screen above that silent disclosure read „Screeningové skóre je **dobře kalibrované** … Automatická rozhodnutí na tomto skóre jsou **obhajitelná**." The same one-command test found the clean `holdout` arm (built *because of* that finding, selector typed `"pipeline" | "analysis"`, no UI, no i18n key in 4 locales), the only channel-spend input (inside a panel no section imports), the empty-state guard `hasNoStageTransitions()` (orphaned), a dead `?funnelEmpty=1` flag, and ~9 orphaned modules whose payload fields the server still computes every request. **This class is near-invisible to L2 alone** — the screen just looks confident — and it is precisely what a consolidation/refactor produces: the machinery is kept, the wiring is dropped. Applied in v1.6 as a **Wiring audit** step beside the grounding audit.

- **The shared-denominator rule (v1.1) was scoped to grounding scores; the same failure recurs for EVERY quantity a run reports.** Three walkers described one defect as "33 panels", "35 briefed" and "40 clean modules + 9 orphaned" — not disagreement, three different units (files vs. briefed files vs. modules vs. barrel exports). Nothing in the method said which unit answers the question, so the synthesis had to arbitrate three rulers again. For reachability the only ratio that answers "is this rendered anywhere" is **chunk/barrel declarations vs. actual imports**. Applied in v1.6: define the unit of any reported count in the overlay, not in the walker.

- **A UAT run writes state that later runs — and users — read as product data.** The seeded host rendered `833 CZK / přijetí` as a live cost-per-hire. The entire figure came from **one** `channel_spend` row (`linkedin = 5,000 CZK, updated_at 2026-07-05`) typed in by *this project's own UAT run six weeks earlier*, when the input still had a home; the consolidation then orphaned that input, so the number became un-updatable while continuing to look current. This cuts both ways: the walker's L1 claim ("cost per hire can never exist, `not_measurable` forever") was **falsified** by the live host, and the truth was *worse* than the claim — a stale number nobody can correct, invisible because it is plausible. Applied in v1.6 under fixture readiness: L2 records its own writes, and preflight traces the provenance of unexplained singleton/round-number rows before any finding cites them as product fact.

- *(Not a method change — a confirmation worth keeping.)* v1.5's preflight discipline paid for itself five times in one run, and twice decisively: `GET /api/analytics/spend` → **405** is *correct* (the route is POST-only), and a raw `feedback.railLabel` key on the empty-tenant host was the **stale-catalog artifact v1.4 predicted**, not a missing translation — the catalog held the Czech string on disk and the other host, started after the edit, rendered it fine. That is the second consecutive run where the freshness rule stopped a phantom i18n regression, and the first where the arms failed asymmetrically *by host* rather than *by locale*. The orchestrator also retracted one lead before dispatch and a walker retracted one of her own mid-run; both retractions are recorded in the run artifacts, which is the habit the `HYPOTHESIS` labelling rule was meant to build.

- *(Observation, no change proposed.)* The gate held correctly and is worth stating plainly: **all three Characters returned `L1-fail`, so no journey earned L2 certification** — yet a *targeted* live pass on the three blockers was still the right spend, because it confirmed two, widened one, and falsified a fourth claim outright. "L1-fail ⇒ no browser time" should stay a rule about **certification**, not about **evidence**; the run's strongest artifacts came from spending ~20 minutes of browser on findings that were already disqualifying.

## 1.6 — 2026-08-18 — CandiDate (retention pass; applied as v1.7)

- **The run store bloats on exactly the axis nobody reads back.** At 8 runs, uat/ was 82 MB: 75 MB screenshots, ~7 MB for every finding, report and Character voice ever produced — and stem-matching citations (reports cite brace-style, `shot.{png,text.txt}`, so basename grep undercounts) showed half the pixels were referenced by no document at all. The policy that survived scrutiny: text is the record, pixels are working evidence — uncited shots go anytime, cited shots go when the run is superseded as its journey's latest, text never goes, and every prune writes a `PRUNED.md` into the run so the thinning is itself on the record. 82 → 24 MB with zero loss of quoted evidence.
- **A naive lifecycle count institutionalizes a lie: 413 "open" findings, honest number 16.** Three separate causes, each needing its own classification rather than a fix-up: strength rows in early runs carried no `resolution` and read as eternally-open defects (detect by id/title/verdict, never by resolution); some early rows carried free text in `resolution` (label `unstamped`, never coerce); and whole runs predated the stamping discipline, their backlogs tracked and closed in an external doc (label the RUN `archived` and its rows `unstamped-at-archive`). Retroactively stamping them "fixed" would have been fabricating history; counting them open would have drowned the 16 real ones. The honest label beats both.
- **The lifecycle ledger is what makes recurrence detection cheap enough to actually happen.** The recurrence-2 findings this project accumulated trace to one cost: answering "has this been raised before?" meant re-reading N runs' findings files, so it didn't happen. A generated `history.json` (id → every run → resolution → ceiling) turns that into a lookup, and a compact generated summary in the repo's TRACKED docs is what survives when the store is local-only. Generated, never hand-written — a hand-maintained history is the "as of W9-3" snapshot problem wearing a new hat.
