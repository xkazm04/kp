# contest overlay - kp

## Engines
All three CLIs resolve on PATH here (`claude`, `codex`, `grok`) - no `CONTEST_*_BIN` override needed.

**Panel composition note.** kp's default participants are BOTH `claude` seats, so the skill's rule ("no judge
shares a family with every participant") is satisfiable only by judging from the other two families. The default
panel above is therefore Codex + Grok, and no self-preference disclosure is required for a Claude-only field.

## Data
kp stages material by exporting its own seeded demo corpus read-only. `data/kp.sqlite` is the OPERATOR'S
live DB - open it `readonly=True` and never write to it. Node cannot be relied on for this: `better-sqlite3`
is a native module and this checkout's `node_modules` has been empty more than once, so the export script
uses Python's stdlib `sqlite3` instead.

Any field a prototype needs that kp does not persist yet must be generated by the export script and marked
`"synthetic": true` in `data/SCHEMA.md`, per phase - a contest brief that silently mixes real and invented
data teaches the panel nothing about the real shape.

## Taste
- **Density with dignity.** kp surfaces carry a lot per screen; a design that only works at 8 items is a
  failure here, and one that reaches density by shrinking type below ~12px is also a failure.
- **Honest absence.** "Nothing happened" and "we never recorded this" must never render identically.
- **Dual theme is coming.** A variant need not implement dark mode, but a design whose whole idea depends on
  one fixed palette migrates badly - kp ships Studio Light and Spark Dark from one codebase.
- **No hover-only information.** kp gates hardcoded aria-labels and ships to 4 locales; anything reachable
  only by hover is a migration defect, not a polish item.
